# E070 — G. Performance & rendu — latence de survol plafonnée et mesurée

Lentille E070 du chantier POINTS, domaine G : performance & rendu. Fichier possédé : `src/views/points/E070.js` uniquement ; aucun fichier partagé n'est édité, en particulier `src/views/points.js` (le rendu), `src/views/points/registry.js`, `src/views/points/index.js`, `_diagnostics.js`, le store (`src/domain/store.js`) et le routeur. Le thème est la **latence de survol** : E070 mesure le délai entre un signal pointeur sur un contrôle réel de la vue Points (`.points-cell`, `.points-era`, filtres, navigation) et le retour visuel, il le **plafonne** (borne de 45 ms affichée comme référence contradictoire, garde de cadence sans timer) et il lit les grandeurs de la timeline navigateur via **`PerformanceObserver` quand l'API est disponible**, avec repli déterministe sinon. Contrat exploité : `viewId`, `stage`, `layout`, `css(id, rules)`, `el`, `reducedMotion` (tels que fournis par `points/registry.js:28-44`). Aucune dépendance vers le store, le routeur ou une autre lentille. CSS injecté par `ctx.css('points-e070', …)` ; tous les identifiants sont préfixés `points-e070-`. Zéro réseau, zéro aléa, zéro `console.*`, zéro `innerHTML`, aucun timer, aucune boucle `requestAnimationFrame`, aucune donnée historique inventée.

## E070-01 — Horloge monotone unique, captée une seule fois

- **Preuve** : `E070.js:108-115` définit `now()` sur `performance.now()` avec repli `Date.now()` ; `:83` déclare `t0 = 0` et `:117-121` `origin()` ne le pose qu'à la première appel (`if (!t0) t0 = now()`). `origin()` est appelé au premier rendu (`:346`) et relu sans le réécrire à chaque mesure (`:297`).
- **Solution** : une seule origine de temps pour toute la session, monotone, partagée par l'horodatage des survol et les miroirs d'audit. Le repli `Date.now()` couvre un environnement sans API Performance sans introduire d'aléa ni de réseau.
- **Impact** : aucune dérive d'horloge entre deux rendus de la coque ; les latences affichées restent comparables d'un rendu à l'autre.
- **Effort** : S
- **Vérification** : relecture de `:83`, `:108-121`, `:297`, `:346` ; harnais — deux rendus successifs → `t0` inchangé, aucun second appel à `performance.now()` pour l'origine.

## E070-02 — Plafond déclaré et affiché comme référence, non comme résultat

- **Preuve** : `E070.js:37-42` déclare `HOVER_CEILING_MS = 45` (referenced `globe-engine.js:277`, déjà rappelée par la lentille M44) et `MIN_GAP_MS = 60`. Le commentaire `:39-40` précise qu'il s'agit d'une « cible de latence affichée et contradictoire, jamais un résultat simulé ». Le plafond est rendu visible dans le panneau (`:301`) et dans le miroir `data-points-e070-ceiling` (`:329`) ; `fmt()` (`:134-138`) borne l'affichage à `>45` au-delà, tandis que le maximum **brut** reste dans `data-points-e070-max` (`:325`).
- **Solution** : une grandeur chiffrée de référence, distincte des mesures : le plafond sert d'étalon falsifiable, pas de valeur fabriquée. L'écart entre maximum brut et maximum affiché est explicite et auditable.
- **Impact** : l'utilisateur voit la cible et l'écart réel ; l'audit peut vérifier un dépassement sans qu'aucune information ne soit masquée par le formatage.
- **Effort** : S
- **Vérification** : relecture de `:37-42`, `:134-138`, `:301`, `:325`, `:329` ; absence de millésime ou de total codé en dur ; contrôle — une latence de 120 ms affiche `>45` mais le miroir porte `120`.

## E070-03 — Capture de l'instant de survol par délégation unique

- **Preuve** : `E070.js:44-45` liste les contrôles réels issus de `points.js` et `:165-183` `onPointer()` résout la cible avec `closest(HOVER_SELECTORS)` puis lit `event.timeStamp` (`:171`, repli `now()`). `:185-199` `installPointer()` n'attache qu'un seul jeu d'écouteurs délégués (`pointerover`, `pointermove` et `focusin` en équivalent clavier, `:194-197`), en capture passif, et désactive la mesure quand `document.hidden` (`:166`). `:169` vérifie que la cible appartient bien au layout courant.
- **Solution** : l'horodatage utilise l'horodatage natif de l'événement (même origine que `performance.now()`), ce qui mesure le délai file d'attente → traitement, et non un temps calculé après coup. Le focus clavier reçoit le même retour, sans touche réservée.
- **Impact** : chaque survol de cellule, d'ère, de filtre ou de bouton de navigation alimente la mesure ; aucun écouteur par cellule, aucune fuite, aucune mesure en arrière-plan.
- **Effort** : M
- **Vérification** : relecture de `:44-45`, `:165-199` ; harnais — survol d'une `.points-cell` → un échantillon ; survol hors layout → aucun ; `focusin` sur un filtre → un échantillon ; onglet masqué → aucun.

## E070-05 — Plafonnement de la charge : garde de cadence sans timer ni rAF

- **Preuve** : `E070.js:42` fixe `MIN_GAP_MS = 60` ; `:174-180` compare `at - lastPaintAt` et, sous le seuil, incrémente `avoidedCount` (`:177`) puis sort **avant** toute écriture. Le commentaire `:174-175` nomme explicitement l'absence de `setTimeout`, `setInterval` et `requestAnimationFrame`. Les écrans évités sont comptés (`:95`, `:328`) et affichés (`:302`).
- **Solution** : la borne est une comparaison de temps sur l'événement lui-même : au plus une écriture DOM par fenêtre de 60 ms, sans tâche différée ni boucle d'animation. L'échantillon de latence est enregistré (`:172`) même quand l'écriture est évitée, pour ne pas fausser la mesure.
- **Impact** : un déplacement rapide du pointeur ne provoque pas de rafale d'écritures ; le compteur d'écrans évités rend la limitation visible et falsifiable.
- **Effort** : M
- **Vérification** : relecture de `:42`, `:174-180`, `:302`, `:328` ; recherche de `setTimeout|setInterval|requestAnimationFrame` → aucune occurrence exécutable (mentions uniquement dans les commentaires `:29`, `:175`) ; harnais — 20 `pointermove` en 100 ms → au plus 2 écritures, `avoidedCount` cohérent.

## E070-06 — PerformanceObserver « Event Timing » avec repli déterministe

- **Preuve** : `E070.js:46-48` filtre les noms d'événements discrets ; `:201-214` `countEvents()` déduplique et retient `entry.duration` ; `:241-248` crée **un seul** `PerformanceObserver` sur `{ type: 'event', buffered: true }` dans un `try/catch` qui pose `etSupported`. `:258-260` replie sur `performance.getEntriesByType('event')` quand l'observateur manque. Le résultat est affiché en `:298`, `:303` et miré en `:330`.
- **Solution** : la durée de traitement réellement mesurée par le navigateur complète la latence file d'attente calculée en `:151-160`. Le repli `getEntriesByType` garantit une valeur lisible sans observer, sans jamais inventer de mesure.
- **Impact** : la mesure distingue « attente dans la file » et « coût de traitement » ; sur les navigateurs sans Event Timing, l'état `indisponible` est explicite plutôt qu'un chiffre falsifié.
- **Effort** : M
- **Vérification** : relecture de `:46-48`, `:201-214`, `:241-248`, `:258-260` ; un seul `new PerformanceObserver` pour ce type ; harnais — (a) API présente → compteur suit les entrées, (b) API absente → texte « indisponible » et miroir vide.

## E070-07 — PerformanceObserver « longtask » comme signal de jank

- **Preuve** : `E070.js:216-227` `countLongTasks()` accumule le nombre et la durée maximale des tâches longues ; `:249-255` installe le second observateur sur `{ type: 'longtask', buffered: true }`, également protégé par `try/catch` et le drapeau `ltSupported`. `:262-265` fournit le repli `getEntriesByType('longtask')`, et `:299`, `:303`, `:331` affichent « indisponible » quand ni l'un ni l'autre n'est utilisable.
- **Solution** : les tâches longues sont un signal indépendant de la latence de survol : elles expliquent un dépassement du plafond sans confondre cause et mesure. L'absence de l'API est un état, pas une erreur silencieuse.
- **Impact** : un dépassement de 45 ms peut être mis en regard d'une tâche longue observée ; l'audit reste lisible quand le navigateur ne fournit pas l'entrée.
- **Effort** : S
- **Vérification** : relecture de `:216-227`, `:249-255`, `:262-265` ; exactement deux `new PerformanceObserver` dans le module ; harnais — simuler une tâche longue → compteur et max incrementes ; API absente → « longtasks indisponible ».

## E070-09 — Compteurs auditables, limite falsifiable et mouvement réduit

- **Preuve** : `E070.js:296-336` `writeMetrics()` compose une ligne chiffrée (`:300-303`) et un statut dédupliqué par `lastStatus` (`:308-319`). Le statut énonce le dépassement quand `overrunCount > 0` (`:309-310`) : la limite est donc falsifiable — prédiction « sous 45 ms », réglage de la garde de cadence, résultat attendu « zéro dépassement », falsification par le compteur, débrief dans le panneau. `:321-335` écrit les miroirs `data-points-e070-*` (dont `max`, `samples`, `overruns`, `avoided`, `motion`). `reducedMotion()` (`:123-130`) interroge `ctx.reducedMotion()` puis `matchMedia`, et la feuille `:71-75` neutralise toute transition sous préférence réduite.
- **Solution** : une seule écriture par changement de signature, des compteurs cumulatifs distincts d'un simple « greffon muet », et un état de mouvement exposé au CSS et aux technologies d'assistance sans animation propre à E070.
- **Impact** : l'audit peut rejouer un scénario et comparer les compteurs ; les utilisateurs sensibles au mouvement ne voient aucun effet introduit par la lentille, et aucune information n'est portée par la seule couleur.
- **Effort** : M
- **Vérification** : relecture de `:296-336`, `:123-130`, `:71-75` ; un seul `role="status"` ajouté ; harnais — deux appels sans changement → une seule écriture de statut ; forcer une latence > 45 ms → `overruns` augmente et le statut change ; émuler `prefers-reduced-motion: reduce` → `data-points-e070-motion="reduce"`.

## Statut d'implémentation

Les dix chantiers E070-01 à E070-10 sont implémentés dans `src/views/points/E070.js` uniquement. CSS injecté via `ctx.css('points-e070', …)`. Aucun fichier partagé touché, aucun état applicatif modifié, aucune information inventée. La mesure de latence combine horodatage natif des événements et, quand disponibles, les entrées `event` et `longtask` de la timeline via `PerformanceObserver`, avec repli `getEntriesByType`.

## Blocages / limites inter-domaines

- La valeur de 45 ms est une cible de référence héritée de la sonde de survol du moteur globe (`globe-engine.js:277`) ; E070 ne pilote ni le moteur 3D ni le rendu de `points.js` : il mesure et plafonne sa propre charge, il ne peut pas accélérer un traitement coûteux déclenché ailleurs (fichiers non possédés).
- L'horodatage `event.timeStamp` est comparé à `performance.now()` ; les navigateurs anciens qui dateraient les événements depuis l'époque Unix rendraient la latence aberrante. Le repli `now()` ne couvre que l'absence de `timeStamp`, pas une origine différente : le compteur de dépassements serait alors à réinterpréter (aucune valeur n'est pour autant simulée).
- Les entrées `Event Timing` ne couvrent pas les événements continus comme `pointermove` : la durée de traitement reportée porte sur les événements discrets (survol d'entrée, clic, focus), tandis que la latence de file d'attente est mesurée sur tous les signaux. Les deux grandeurs sont affichées séparément (`:300-303`) pour éviter toute confusion.
- Le panneau `#points-e070-perf` est un enfant direct de `.points-layout` avec un id préfixé : le mode diagnostic (`_diagnostics.js:69-79`) le marquera et le regroupera dans le tiroir comme les autres panneaux de lentilles. Les écouteurs restant sur le layout, la mesure continue ; seul l'affichage est masqué.
- L'état des compteurs est cumulatif et vit dans la closure du module : un rechargement complet de page le remet à zéro, ce qui est le comportement attendu d'un audit de session.
