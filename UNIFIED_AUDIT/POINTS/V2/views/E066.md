# E066 (passe 2) — Performance & rendu : signature anti-écriture redondante

Lentille E066 — domaine G : performance & rendu, deuxième passe du module
POINTS E066. Fichier possédé : `src/views/points/v2/E066.js` uniquement. Aucun
fichier partagé (`points.js`, `points/v2/registry.js`, `points/v2/index.js`,
`styles.css`, `_diagnostics.js`) n'est modifié ; la passe 1
(`src/views/points/E066.js`), son panneau `#points-e066-panel` et son
`MutationObserver` ne sont ni lus pour écriture ni doublés. Aucune autre
lentille (E027, E047) n'est touchée.

La vue `points.js:128` appelle `runEnhancementsV2({ viewId: 'pointsv2', stage,
layout })` en plus de la passe 1 (`points.js:127`). Le greffon V2 est donc
indépendant et coexistant : il ajoute un banc de mesure local, en flux normal,
qui rend auditable la règle « n'écrire dans le DOM que lorsqu'une valeur a
réellement changé ». Contrat exploité : `ctx = { viewId, stage, layout, css, el,
reducedMotion }`. Espace de noms exclusif : `points-v2-e066` pour la feuille, la
classe de portée, les ids, les classes internes et les attributs
`data-points-v2-e066-*` — jamais `points-e066` ni `points-v2-e027`.

Tout DOM statique est bâti avec `ctx.el` (jamais `innerHTML`). Zéro réseau,
zéro `Math.random`, zéro date, zéro `console.*`, zéro timer, zéro rAF, zéro
écouteur global. Les deux signaux A et B du banc sont des entrées de mesure
explicitement présentées comme telles : aucun libellé de point, aucune ère,
aucune certitude, aucune source n'est fabriqué.

## E066-V2-01 — Feuille unique préfixée et portée ancrée sur la vue

- **Problème / preuve** : `points/v2/registry.js:13-19` protège la feuille par
  id (`cssOnce`) mais `runEnhancements` rejoue les greffons à chaque rendu
  (`:28-43`) ; sans portée dédiée, une règle pourrait fuir vers la passe 1.
- **Solution** : `E066.js:30-47` déclare un seul `CSS_ID = 'points-v2-e066'`,
  une classe de portée, dix ids préfixés, deux classes d'état, un préfixe de
  données et une variable CSS privée. La feuille `E066.js:54-106` ne contient
  que des sélecteurs `.points-v2-e066 …`, y compris dans les trois requêtes
  `@media`. `install()` l'injecte une seule fois via `ctx.css(CSS_ID, CSS)`
  (`:322`) et pose la classe sur la racine commune (`:326`).
- **Impact** : aucune collision avec les 99 autres lentilles ni avec la coque ;
  la portée est plus étroite que la vue Points et suit le panneau où qu'il soit
  déplacé.
- **Risque** : l'ancrage dépend de la racine retournée par `anchors()` (`:142-149`) ;
  en repli sur `document.body`, la portée reste portée par la classe, donc
  toujours limitée aux nœuds `points-v2-e066-*`.
- **Effort** : S.
- **Vérification** : relecture `:30-47`, `:54-106`, `:322`, `:326` ; navigation
  aller-retour → un seul `<style id="points-v2-e066">` dans `<head>`.

## E066-V2-02 — Texte conditionnel

- **Problème / preuve** : `registry.js:21-26` pose `node.textContent = text` sans
  comparaison et le registre rejoue les greffons à chaque rendu
  (`registry.js:39-42`) : un libellé identique est réécrit pour rien.
- **Solution** : `putText()` (`E066.js:153-158`) compare `node.textContent` avant
  d'écrire, compte l'évitement dans `stats.text.s` (`:155`) et l'écriture dans
  `stats.text.w` (`:157`). Les cinq lignes variables passent par là
  (`:277-281`) ; le titre et le préambule figés sont écrits une seule fois à
  l'installation (`:334`, `:336`).
- **Impact** : un cycle sans changement de libellé ne touche aucun nœud de
  texte ; le gain est lisible dans `#points-v2-e066-counters` et dans
  `data-points-v2-e066-w-text` / `-s-text`.
- **Risque** : un texte modifié extérieurement serait écrasé par la valeur
  mémorisée ; c'est un choix de périmètre assumé — le panneau est le seul
  propriétaire de ses nœuds.
- **Effort** : S.
- **Vérification** : relecture `:153-158` ; harnais — appeler
  `panel.pointsV2E066Refresh()` deux fois sans changer les signaux : `s-text`
  augmente, `w-text` reste constant.

## E066-V2-03 — Attributs ARIA conditionnels

- **Problème / preuve** : aucun garde n'empêche un `setAttribute` répété à
  valeur égale sur `role`, `aria-labelledby` et `aria-describedby` ; cela
  invalide le style du panneau à chaque cycle.
- **Solution** : `putAttr()` (`E066.js:163-169`) compare par `getAttribute`
  (`:165`), n'écrit qu'en cas de différence (`:166`) et comptabilise les deux
  issues. Les trois attributs sont posés en `:273-275`.
- **Impact** : les attributs d'accessibilité restent stables entre les rendus ;
  `data-points-v2-e066-w-attr` / `-s-attr` exposent le résultat.
- **Risque** : un attribut supprimé extérieurement est reposé au cycle suivant
  — comportement recherché de robustesse. Aucun conflit : les ids référencés
  sont tous préfixés `points-v2-e066-`.
- **Effort** : S.
- **Vérification** : relecture — aucun `setAttribute` direct dans `commit()`
  (`:272-302`) en dehors du canal de télémétrie ; harnais — `w-attr` plafonne à
  3 après le premier cycle.

## E066-V2-04 — Attributs `data-*` préfixés et gardés

- **Problème / preuve** : la passe 1 utilise déjà un `MutationObserver`
  (`src/views/points/E066.js:181-200`) ; écrire des `data-*` à chaque cycle
  générerait des mutations parasites dans la vue.
- **Solution** : `putData()` (`E066.js:173-179`) construit le nom complet
  `data-points-v2-e066-<clé>` via `DATA_PREFIX` (`:46`, `:175`), compare avec
  `getAttribute` et ne pose que si la valeur diffère. État, phase, garde et
  signature empruntent ce canal (`:276-278`).
- **Impact** : aucune mutation de dataset redondante sur le canal mesuré ;
  `data-points-v2-e066-w-data` / `-s-data` prouvent l'évitement.
- **Risque** : la télémétrie (chantier 09) écrit elle aussi des attributs
  préfixés, mais via `rawData` et avec de vraies valeurs qui évoluent : ce ne
  sont pas des écritures redondantes.
- **Effort** : S.
- **Vérification** : relecture `:46`, `:173-179`, `:276-278` ; harnais — cycles
  identiques répétés : `w-data` n'augmente que pour `gated` et `state` quand
  ils changent réellement.

## E066-V2-05 — Classes basculées sous test de présence

- **Problème / preuve** : un `classList.add/remove` inconditionnel force un
  recalcul de style même si la classe est déjà dans l'état voulu.
- **Solution** : `putClass()` (`E066.js:183-190`) lit `classList.contains`
  (`:185`), compte l'évitement si l'état voulu est déjà atteint (`:186`) et ne
  mute qu'en cas de bascule (`:187-188`). Les classes
  `points-v2-e066-stable` / `points-v2-e066-dirty` sont pilotées en
  `:282-283`, avec un style de bordure distinct (`:64-65`) **et** le mot
  « état stable » / « changement détecté » porté par le texte de la signature
  (`:261`), jamais la couleur seule.
- **Impact** : le panneau ne change de classe qu'au basculement réel de
  l'empreinte ; `data-points-v2-e066-w-cls` / `-s-cls` le quantifient.
- **Risque** : l'état est dérivé de la seule empreinte du banc ; il ne prétend
  pas décrire l'état global de la vue Points.
- **Effort** : S.
- **Vérification** : relecture `:183-190`, `:64-65`, `:261`, `:282-283` ;
  harnais — premier cycle : `dirty` ; cycle identique : `stable` ; troisième
  cycle : aucune écriture de classe.

## E066-V2-06 — Variable CSS de style posée seulement si modifiée

- **Problème / preuve** : poser `--points-v2-e066-ratio` à chaque rendu invalide
  le style du panneau et de la barre qui le consomme.
- **Solution** : `putStyle()` (`E066.js:195-201`) compare
  `node.style.getPropertyValue(property)` (`:197`) avant `setProperty`
  (`:198`). La variable `RATIO_VAR` (`:47`) est posée en `:284` et consommée
  par `.points-v2-e066-bar` via `width: calc(var(--points-v2-e066-ratio, 0) * 1%)`
  (`:84-87`).
- **Impact** : la largeur de la barre ne bouge que si le ratio d'économie change
  vraiment ; effet observable et `data-points-v2-e066-w-style` / `-s-style`.
- **Risque** : le ratio dépend des compteurs, donc il évolue les premiers cycles
  puis se stabilise ; la transition CSS est neutralisée en mouvement réduit
  (`:92-95`).
- **Effort** : S.
- **Vérification** : relecture `:195-201` ↔ `:84-87` ; harnais — lire
  `getPropertyValue('--points-v2-e066-ratio')` avant/après un cycle sans
  changement : inchangé, et `s-style` incrémenté.

## E066-V2-07 — Empreinte déterministe et garde de non-recalcul

- **Problème / preuve** : `registry.js:39-42` rejoue systématiquement
  `apply(api)` ; sans empreinte, le greffon ne distingue pas « état inchangé »
  de « état modifié » et recalcule ses valeurs dérivées à chaque fois.
- **Solution** : `signatureOf()` (`E066.js:240-246`) calcule un hachage djb2
  déterministe (`:243-245`) sur `viewId`, signaux A/B et préférence de
  mouvement (`:242`), sans aléa ni date. `refresh()` (`:304-312`) compare à
  l'empreinte mémorisée sur le nœud (`:307`), incrémente `gateHits` (`:308`,
  compteur module `:112`) et réutilise les valeurs mémorisées (`:309`) quand
  rien n'a changé, puis réécrit la mémoire (`:311-312`).
- **Impact** : un cycle sans changement ne recalcule aucune valeur dérivée ;
  `data-points-v2-e066-gated` et le mot porté par la signature rendent l'état
  stable visible.
- **Risque** : le hachage 32 bits peut théoriquement entrer en collision ;
  l'empreinte n'est qu'un garde-fou de performance, jamais une preuve
  d'identité — les valeurs affichées restent dérivées des signaux lus
  (`:251-266`).
- **Effort** : M.
- **Vérification** : relecture `:240-246`, `:304-312` ; harnais — modifier
  `data-points-v2-e066-signal-a` puis rejouer le hook : l'empreinte change et
  les textes sont réécrits ; rappeler sans modifier : empreinte identique,
  `gated` incrémenté.

## E066-V2-08 — Phases de lecture et d'écriture groupées

- **Problème / preuve** : lire un attribut, écrire, puis relire force des
  allers-retours coûteux entre script et mise en page ; le registre ne structure
  pas les greffons en phases.
- **Solution** : `collect()` (`E066.js:229-235`) regroupe les deux signaux
  (`:231-232`) et la préférence de mouvement (`:233`) en une seule passe,
  avec `collectPasses` incrémenté (`:230`). `commit()` (`:272-302`) regroupe
  toutes les comparaisons et mutations, sans lecture intermédiaire.
  `refresh()` ordonnance explicitement les deux phases (`:305` puis `:310`).
  Le libellé de phase est publié en `:263` et `:281`.
- **Impact** : une seule passe de lecture par cycle ; le nombre de passes est
  auditable via `#points-v2-e066-phase` et `data-points-v2-e066-phase`.
- **Risque** : les signaux sont lus au début du cycle ; une mutation concurrente
  pendant `commit()` ne serait prise en compte qu'au cycle suivant — accessoire
  pour un banc non interactif.
- **Effort** : M.
- **Vérification** : relecture — aucun `getAttribute`, `dataset` ou
  `getPropertyValue` dans `commit()` hors `putAttr`/`putData`/`putStyle` ;
  harnais — une seule augmentation de `collectPasses` par appel au hook.

## E066-V2-09 — Télémétrie séparée du canal mesuré

- **Problème / preuve** : si les compteurs d'écritures étaient incrémentés par
  l'acte de les publier, ils s'auto-alimenteraient et le chiffre perdrait tout
  sens ; le registre n'expose aucun canal de télémétrie dédié.
- **Solution** : `rawText()` / `rawData()` (`E066.js:204-211`) comparent avant
  d'écrire mais ne touchent jamais `stats`. `totalWrites()`, `totalSkips()` et
  `ratioOf()` (`:213-223`) calculent les agrégats ; `derive()` construit le
  registre de bord (`:262`, `:264`) ; la publication a lieu en `:287-302`. Le champ
  `stats` est réinitialisable via `newStats()` (`:113`, `:115-123`).
- **Impact** : les chiffres affichés décrivent la charge mesurée réelle, pas
  l'instrumentation ; le ratio pilote aussi la barre (`:255`, `:284`).
- **Risque** : les compteurs publiés sont un instantané pris au début de
  `commit()` ; quelques écritures de données effectuées ensuite ne sont
  visibles qu'au cycle suivant — hypothèse documentée.
- **Effort** : M.
- **Vérification** : relecture — zéro appel à `putText`/`putData` dans le bloc
  de télémétrie (`:287-302`) ; harnais — deux cycles identiques :
  `data-points-v2-e066-skips` augmente, `w-*` n'augmente que pour les changements
  réels (`gated`, `state`).

## E066-V2-10 — Idempotence, accessibilité et hook de mesure vérifiable

- **Problème / preuve** : `registry.js:13-19` protège la feuille par id mais
  `registry.js:39-42` rejoue tous les greffons ; la coque vide le stage avant
  de relancer les améliorations. Sans garde, panneau, signaux et crochet
  seraient recréés à chaque rendu. Une mesure invisible, elle, ne peut être ni
  audité ni falsifié.
- **Solution** : `ensureNode()` (`:129-137`) réutilise un nœud par id préfixé et
  le déplace dans le parent courant ; `anchors()` (`:142-149`) choisit la
  matrice, le layout ou le stage. Les signaux ne sont posés que s'ils manquent
  (`:330-331`), les enfants sont réordonnés par `replaceChildren` sans doublon
  (`:345`) et la barre est réattachée si nécessaire (`:346`). L'empreinte est
  ancrée sur le nœud (`:307`, `:311-312`). Un seul `register('E066', …)` est
  émis (`:353`) et un seul `ctx.css` (`:322`). Le panneau est une région
  intitulée (`:273-275`, `:333-336`) en flux normal, jamais modale ; le titre,
  le préambule et cinq lignes de texte sont lisibles, avec repli 620 px
  (`:88-91`), `prefers-reduced-motion` (`:92-95`) et `forced-colors`
  (`:96-105`). Le crochet `panel.pointsV2E066Refresh()` (`:349`) permet de
  rejouer un cycle sans recréer le panneau. Aucune région live, aucun `focus()`,
  aucun gestionnaire d'événement n'est ajouté.
- **Impact** : aucun doublon de panneau, de feuille ou de crochet après
  navigation aller-retour ; l'économie d'écritures est lisible, mesurable et
  reproductible en 390×844 comme sur écran large ; l'état est porté par le texte
  et le style de bordure, pas par la couleur seule.
- **Risque** : le panneau allonge légèrement la matrice ; c'est le compromis
  assumé face à un panneau absolu qui recouvrirait la grille. Si la coque
  détruit le stage, un panneau neuf est créé et la mémoire d'empreinte repart
  de zéro, ce qui est correct ; `data-points-v2-e066-installs` rend le cas
  visible.
- **Effort** : M.
- **Vérification** : `node --check src/views/points/v2/E066.js` PASS ; relecture
  — un seul `register` (`:353`), un seul `ctx.css` (`:322`), dix ids préfixés
  `points-v2-e066-` (`:32-41`) ; harnais — rendu → navigation → rendu : un seul
  `#points-v2-e066-panel` et un seul `<style id="points-v2-e066">`. Émuler
  `prefers-reduced-motion: reduce` et `forced-colors: active` : aucune
  transition, information conservée.

## Statut d'implémentation

Les dix chantiers E066-V2-01 à E066-V2-10 sont **implémentés** dans
`src/views/points/v2/E066.js` uniquement. Une seule feuille CSS injectée par
`ctx.css('points-v2-e066', CSS)` (`:322`), entièrement préfixée `.points-v2-e066`.
Dix ids uniques préfixés `points-v2-e066-` (`:32-41`), avec garde d'existence
(`:129-137`). Un seul `register('E066', ctx => …)` (`:353`). Tout DOM statique
est bâti par `ctx.el` (`:328-346`) ; aucune chaîne HTML n'est réinterprétée.
Toute écriture mesurée passe par l'une des cinq fonctions comparantes
(`:153-201`) ou par le canal de télémétrie non compté (`:204-211`). Aucun
fichier partagé modifié, aucune donnée de point inventée, aucune annonce live
ajoutée, aucune animation JS.

## Blocages / limites inter-domaines

- L'anti-redondance est propre au greffon E066 V2 : elle ne protège pas les
  écritures des autres lentilles ni celles de la vue `points.js`, qui
  reconstruit son layout à chaque changement d'état.
- L'empreinte (`:240-246`) ne couvre que les entrées du banc (`viewId`, signaux
  A/B, mouvement réduit). Les signaux A et B sont des entrées de mesure
  modifiables, distinctes des données réelles de la vue : le banc ne prétend pas
  détecter un changement de grille, de filtre ou de détail. Une signature
  inter-lentilles relèverait du maître d'œuvre.
- `panel.pointsV2E066Refresh()` (`:349`) est un hook de mesure, pas un
  abonnement : aucun événement n'est capté, aucun `MutationObserver` n'est créé
  en V2 (la passe 1 garde le sien). Un harnais doit appeler explicitement le
  crochet après avoir modifié les signaux.
- Les compteurs sont volatils et dépendent de l'historique des cycles depuis le
  chargement ; `data-points-v2-e066-installs` permet de repérer un re-render,
  mais un rechargement complet les remet à zéro.
- Aucune mesure de latence ni de canvas n'est réalisée : le chantier se limite
  aux écritures DOM. Les chantiers de budget canvas et de latence de survol
  restent hors périmètre.
