## E061-01 — Boucle rAF : zéro animation instanciée par la lentille

- **Problème / preuve** : le stub initial (`E061.js:1-4` avant remplacement) se limitait à `register('E061', () => {})` : aucun état de boucle n'était exposé et le thème même (« rAF unique ou nulle ») restait sans preuve. Le modèle de qualité pose bien « zéro `rAF`, zéro timer » (`UNIFIED_AUDIT/CHRONOLOGIE/views/E049.md:4`) mais énonce l'invariant sans le mesurer, alors que le registre V2 rejoue les greffons à chaque rendu (`registry.js:39-42`) : une lentille naive pourrait installer une boucle par rendu.
- **Solution** : `E061.js:122` fige `PROGRAMMED = { raf: 0, timers: 0, intervals: 0, loops: 0 }` ; `:113-118` analyse la feuille CSS pour compter `animation-name` et `transition-property` ; `:167` affiche « 0 rAF · 0 animation propre · 0 transition propre » et `:183` publie `data-e061-raf="0"`. Le bilan `:180` consolide le compteur. Aucun `requestAnimationFrame` n'est appelé dans le module.
- **Impact** : le choix « boucle nulle » plutôt qu'« unique » est auditable en texte et en attribut ; il n'existe aucune frame à accélérer, donc aucune concurrence avec la coque.
- **Risque** : l'audit CSS ne voit que la feuille de la lentille ; une boucle introduite par une autre lentille ou par la coque échapperait à ce compteur — le périmètre est explicitement borné au module (commentaire `:120-121`).
- **Effort** : S.
- **Vérification** : relecture — aucune occurrence exécutable de `requestAnimationFrame`, seulement la mention en commentaire `:19` ; `#chronology-v2-e061-rafs` affiche `0 rAF` et `data-e061-raf="0"` ; le CSS neutralise tout mouvement hérité (`:84-90`) sans en créer.

## E061-02 — Un seul écouteur `visibilitychange`, sous garde module

- **Problème / preuve** : le stub (`E061.js:4`) n'écoutait rien. Or `runEnhancements` applique chaque greffon à chaque rendu (`registry.js:39-42`), et le modèle E049 consacre son chantier E049-10 à l'unicité de l'écouteur (`E049.md:102-108`) : sans garde, un écouteur `visibilitychange` serait ajouté une fois par navigation, multipliant les rafraîchissements.
- **Solution** : `E061.js:197-210` définit `bindVisibility()` avec la garde `visibilityBound` (`:125`, `:198`) : l'écouteur n'est posé qu'une fois (`:207`) et `:209` pose la garde. `:268` appelle la fonction à chaque rendu sans effet supplémentaire ; `:169` et `:184` exposent l'état de l'écoute (`visibilitychange` / `none`).
- **Impact** : aucune fuite d'écouteur sur une longue session, même après aller-retour entre vues ; un seul rafraîchissement par événement système.
- **Risque** : si `document.addEventListener` est absent (harnais minimal), `:199` retourne `false` et la lentille reste fonctionnelle avec l'état initial seulement — repli explicite dans le libellé `:170`.
- **Effort** : M.
- **Vérification** : relecture — une seule occurrence de `addEventListener('visibilitychange'` (`:207`) ; rejeu rendu → navigation → rendu : `data-e061-listener` reste `visibilitychange` et le compteur de rendus (`:190`) augmente sans duplication d'écoute.

## E061-03 — État `document.hidden` affiché en texte visible, sans région live

- **Problème / preuve** : le modèle signale que le registre fournit `ctx.reducedMotion()` (`E049.md:95`, `registry.js:33-36`) mais qu'aucune préférence n'est exposée en texte lisible ; de même, `document.hidden` reste une valeur interne sans traduction visible. Le stub (`E061.js:3`) n'affichait rien. Ajouter une région live aurait aggravé la concurrence déjà relevée entre trois régions (`E049.md:57-64`).
- **Solution** : `E061.js:164-166` écrit « Document visible / masqué : aucune frame n'est demandée. » dans `#chronology-v2-e061-state` (créé en `:241`) ; `:182` publie `data-e061-hidden="1"` ou `"0"`. Le panneau est un `<section role="region">` ordinaire (`:232-234`), sans `aria-live` ni `role="status"`, et `:149-151` déduplique les écritures.
- **Impact** : l'état de visibilité devient lisible et vérifiable par les technologies d'assistance lors de la navigation dans le panneau, sans annonce spontanée ni bavardage.
- **Risque** : le texte n'est pas annoncé automatiquement ; c'est un choix délibéré pour ne pas ajouter une quatrième région live à une vue déjà bavarde (`E049.md:57-64`).
- **Effort** : S.
- **Vérification** : relecture — zéro `aria-live`, zéro `role="status"` dans le module ; basculer l'onglet → `#chronology-v2-e061-state` suit `document.hidden` et `data-e061-hidden` passe de `0` à `1` puis revient à `0`.

## E061-04 — Pause pendant le masque : aucun rAF ni minuteur armé

- **Problème / preuve** : le modèle cite la neutralisation globale des animations (`E049.md:95`, `styles.css:342-344`) et les transitions de bandes/cartes (`chronology.js:89-91`) ; aucune règle ne dit ce qui se passe quand le document est masqué. Le thème exige précisément une pause sur `document.hidden`, mais le stub (`E061.js:4`) n'implémentait ni pause ni état associé.
- **Solution** : `E061.js:58-60` change la lisière du panneau via `[data-e061-hidden="1"]` **sans transition** ; `:171-173` affiche « Pause : aucune boucle en cours… » quand le document est masqué, sinon « Aucune boucle à suspendre : la boucle est nulle, pas unique. » ; `:185` publie `data-e061-loop="paused"` / `"none"`. Aucun rAF, aucun minuteur n'est armé à quelque moment que ce soit (`:122`).
- **Impact** : la pause est effective par construction : il n'y a pas de boucle à suspendre, donc aucun travail en arrière-plan pendant le masque, et l'état est observable sans ouvrir les outils.
- **Risque** : le changement de lisière reste une modification visuelle unique à l'événement ; il n'est pas animé, ce qui est voulu — une animation de « pause » serait contradictoire avec le chantier E061-01.
- **Effort** : S.
- **Vérification** : émuler un passage en arrière-plan → `data-e061-hidden="1"`, `data-e061-loop="paused"`, libellé « Pause » ; relecture — aucune instruction d'animation ni de minuteur dans `:50-104` et `:197-210`.

## E061-05 — Reprise au retour : un seul rafraîchissement, compteur dédié

- **Problème / preuve** : le registre rejoue les greffons à chaque rendu (`registry.js:39-42`) ; sans garde, chaque retour au visible pourrait déclencher plusieurs `paint()`, et une boucle mal écrite reprendrait autant de fois qu'elle aurait été instanciée. Le stub (`E061.js:4`) ne comptabilisait aucune reprise.
- **Solution** : `E061.js:200-206` mémorise `wasHidden` (`:201`), lit l'état courant (`:202`), incrémente `changes` (`:203`) et n'incrémente `resumes` que sur le passage masqué → visible (`:204`), puis appelle `paint()` une seule fois (`:205`). `:174` affiche le compte dans `#chronology-v2-e061-resumes` et `:186` publie `data-e061-resumes`.
- **Impact** : la reprise est singulière et chiffrée : on peut vérifier qu'un cycle masqué/visible produit exactement une reprise, ni zéro ni plusieurs.
- **Risque** : un événement `visibilitychange` sans changement réel de `document.hidden` incrémente `changes` mais pas `resumes` — comportement voulu, documenté par la séparation des deux compteurs (E061-07).
- **Effort** : M.
- **Vérification** : harnais — masquer puis réafficher → `data-e061-resumes` passe de `0` à `1` ; deux cycles → `2` ; un rendu supplémentaire sans changement de visibilité ne modifie pas le compte.

## E061-06 — Zéro sondage : aucun `setInterval` / `setTimeout` de `document.hidden`

- **Problème / preuve** : une implémentation courante sonde `document.hidden` à intervalle régulier ; le modèle pose « zéro timer » (`E049.md:4`) sans le mesurer, et `styles.css:342-344` (cité en `E049.md:95`) neutralise les animations mais pas un éventuel polling. Le stub (`E061.js:4`) n'offrait aucune garantie sur ce point.
- **Solution** : `E061.js:122` fixe `timers: 0`, `intervals: 0`, `loops: 0` ; `:176` affiche « 0 minuteur · 0 intervalle · 0 boucle : aucun sondage de `document.hidden`. » ; `:188` publie `data-e061-poll="0"`. Le rafraîchissement est exclusivement piloté par l'événement (`:194-210`) et par le rendu (`:266`, `:269`).
- **Impact** : aucun réveil périodique, donc aucun coût CPU en arrière-plan ; l'économie est mesurable par relecture et par l'absence de minuteur dans le module.
- **Risque** : le contrat dépend de la disponibilité de l'événement `visibilitychange` (`:199`) ; le repli est l'état initial figé, sans sonde de secours — choix cohérent avec « zéro polling ».
- **Effort** : S.
- **Vérification** : relecture — aucune occurrence de `setTimeout` ou `setInterval` (seules les mentions de commentaire `:21-22`) ; `data-e061-poll="0"` ; aucune requête périodique observable dans les outils réseau/performance.

## E061-07 — Décompte des changements de visibilité, distinct des reprises

- **Problème / preuve** : le stub (`E061.js:4`) ne conservait aucun compteur ; le modèle E049 maintient ses propres compteurs module (`E049.md:102-108`) pour rendre l'activité auditable. Sans distinction entre « changement observé » et « reprise effective », un événement sans bascule réelle serait confondu avec une reprise.
- **Solution** : `E061.js:203` incrémente `changes` à chaque événement ; `:175` l'affiche dans `#chronology-v2-e061-changes` et `:187` publie `data-e061-changes`. Le bilan `:180` cite séparément `changes` et `resumes`, ce dernier étant réservé aux bascules masqué → visible (`:204`).
- **Impact** : deux mesures complémentaires — volume d'événements système et nombre réel de reprises — permettent de falsifier l'hypothèse d'une boucle qui reprendrait trop souvent.
- **Risque** : le compteur inclut les événements émis sans changement de valeur ; il mesure l'activité du navigateur, pas les actions utilisateur, comme le précise le commentaire `:157-159`.
- **Effort** : S.
- **Vérification** : harnais — deux cycles complets → `data-e061-changes="4"` et `data-e061-resumes="2"` ; forcer un événement sans bascule → `changes` augmente seul ; les deux libellés restent cohérents avec le bilan `:180`.

## E061-08 — Feuille CSS unique et repli `forced-colors` sans mouvement

- **Problème / preuve** : le registre ne protège que l'unicité du `<style>` (`registry.js:13-19`) ; le modèle souligne un contraste fragile (`E049.md:93-100`, indice 8 px en `--muted-2`) et ne prévoit pas de repli pour l'état de visibilité. Une lentille pourrait injecter plusieurs feuilles ou coder l'état par la seule couleur dorée.
- **Solution** : `E061.js:29` définit un unique `CSS_ID`, `:50-104` une seule chaîne CSS passée une seule fois à `ctx.css` (`:227`) ; `:93-103` fournit le repli `Canvas`/`CanvasText` y compris pour `[data-e061-hidden="1"]` (`:98`). `:113-118` mesure les règles d'état et le repli ; `:177` et `:189` en rendent compte en texte et en attribut.
- **Impact** : l'état est lisible même en couleurs forcées et en N&B, par le texte et la bordure, sans aucun mouvement ni dépendance à la teinte.
- **Risque** : `Canvas`/`CanvasText` écrasent les accents dorés — c'est voulu : l'information est portée par le libellé et la lisière, pas par la couleur.
- **Effort** : S.
- **Vérification** : émuler `forced-colors: active` → le panneau reste délimité et les dix libellés lisibles ; relecture — un seul `ctx.css` (`:227`), un seul `<style id="chronology-v2-e061">`, `data-e061-contrast="text+border"`.

## E061-09 — Idempotence multi-rendus et unicité du panneau

- **Problème / preuve** : le stub (`E061.js:1-4`) était vide ; `cssOnce` (`registry.js:13-19`) ne garantit que l'unicité de la feuille, et `runEnhancements` rejoue les greffons à chaque rendu (`registry.js:39-42`). Le modèle E049 traite le même risque (`E049.md:102-108`) : sans garde d'existence, panneaux et IDs se dupliquent après navigation.
- **Solution** : `E061.js:139-147` implémente `ensureNode()` avec `getElementById` et déplacement dans le parent courant ; `:226` compte les installations, `:229-232` résout l'hôte et crée/réutilise le panneau ; `:257` utilise `replaceChildren` ; `:249-250` reconstruit les lignes dans un `<dl>` unique. `:190` publie `data-e061-renders` et `:272-274` impose un seul `register`.
- **Impact** : aucun doublon de panneau, de ligne ou de feuille de style après navigation aller-retour ; les compteurs module survivent aux rendus sans créer de nœud.
- **Risque** : un nœud retrouvé dans un ancien parent détaché est déplacé, jamais cloné (`:145`) ; ses `data-e061-*` sont réécrits à chaque `paint()` (`:182-191`), donc jamais périmés. Le registre neutraliserait silencieusement une erreur : `node --check` reste la première ligne de défense.
- **Effort** : M.
- **Vérification** : `node --check src/views/chronology/v2/E061.js` → PASS ; relecture — un seul `register`, un seul `ctx.css`, treize IDs tous préfixés `chronology-v2-e061-` ; rejeu rendu → navigation → rendu : un seul `#chronology-v2-e061-panel`, une seule feuille, `data-e061-renders` incrémenté de un.

## E061-10 — Écoute purement observationnelle, sans empiètement

- **Problème / preuve** : le modèle rappelle que la vue et la coque gèrent déjà le focus (`E049.md:39-47`, `E049.md:4` : « zéro vol de focus »). Un écouteur qui appellerait `preventDefault()`, `stopPropagation()` ou `focus()` court-circuiterait ces restaurations, exactement comme le risque décrit en E049-03 (`E049.md:39-47`).
- **Solution** : `E061.js:200-206` ne lit que `document.hidden`, incrémente deux compteurs et appelle `paint()` ; aucun `preventDefault`, aucun `stopPropagation`, aucun `focus()` n'apparaît dans le module. `:23-26` posent l'invariant d'en-tête, `:179` l'affiche en texte et `:191` publie `data-e061-intrusion="none"`. Le panneau lui-même n'a pas de `tabindex` (`:232-234`).
- **Impact** : la navigation clavier, la restauration de focus et les filtres existants continuent de fonctionner exactement comme avant ; la lentille n'ajoute aucun arrêt Tab.
- **Risque** : un futur greffon pourrait modifier les mêmes attributs `data-e061-*` ; la lentille ne revendique que son propre panneau et n'écrit dans aucune région existante, ce qui borne le risque de collision.
- **Effort** : S.
- **Vérification** : relecture — zéro `preventDefault`, `stopPropagation`, `focus(`, `tabindex` dans le module ; harnais — Tab/Entrée/flèches conservent leur comportement, `data-e061-intrusion="none"` après re-render.

## Blocages / limites inter-domaines

- La boucle de la vue hôte n'est pas instrumentée : E061 choisit la boucle **nulle** pour son propre panneau et ne peut ni compter ni arrêter un `requestAnimationFrame` qui serait introduit par la coque ou par une autre lentille (le registre V2 est lu seul, non modifié — `registry.js:28-43`).
- Le suivi dépend de l'événement natif `visibilitychange` (`:199`, `:207`) : dans un harnais sans API DOM complète, la lentille retombe sur l'état initial et publie `data-e061-listener="none"`, sans sonde de secours — cohérent avec E061-06.
- Les compteurs `changes`, `resumes` et `installs` sont volatils : ils sont reconstruits à chaque rendu, conformément au contrat de greffon ; ils mesurent l'activité observée, pas les actions utilisateur.
- L'audit CSS (`:113-118`) ne couvre que la feuille de la lentille ; les animations ou transitions éventuellement héritées de `styles.css:342-344` sont neutralisées défensivement (`:84-90`) mais non dénombrées.
- Le registre V2 neutraliserait silencieusement une erreur d'installation (`registry.js:39-42`) : `node --check` et les gardes d'existence constituent la première ligne de défense ; le contrôle visuel final reste à l'agent maître.
