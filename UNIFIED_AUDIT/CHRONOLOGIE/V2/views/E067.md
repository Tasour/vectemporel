## E067-01 — Aucune API d'écriture de balisage brut dans le module

- **Problème / preuve** : le stub initial (`src/views/chronology/v2/E067.js:1-4`, avant remplacement) ne contenait qu'un import, un commentaire et un `register` vide : aucune garantie statique n'empêchait une future lentille d'écrire du balisage sous forme de chaîne. Or le modèle de passe 1 rappelle que le registre rejoue les greffons et que la coque détruit le stage à chaque rendu (`UNIFIED_AUDIT/CHRONOLOGIE/views/E049.md`, chantier E049-10, qui cite `registry.js:39-42` et `shell.js:533`) : toute écriture par chaîne serait réinterprétée à chaque navigation. Les zones exposées sont les libellés (`E067.js:227-238`) et la greffe du panneau (`E067.js:325`).
- **Solution** : `E067.js:54-61` assemble les quatre noms d'API proscrites par concaténation de fragments ; `:70` porte le constat statique `ecritureBrute: 0` ; `:227` affiche « 0 appel » dans `#chronology-v2-e067-api` et `:240` publie `data-e067-raw="0"`. Le commentaire d'en-tête (`:23-25`) explicite pourquoi aucun nom littéral n'apparaît dans le fichier : l'audit statique reste ainsi vérifiable par simple recherche de chaîne.
- **Impact** : une recherche de `inner…HTML`, `outer…HTML`, `insertAdjacent…HTML` et `document.write` dans le module ne renvoie aucune occurrence ; le risque d'interprétation d'une chaîne comme balisage est nul, et cette absence est affichée à l'utilisateur.
- **Risque** : le compteur `0` est un fait structurel vérifié par relecture, comme le compteur `PROGRAMMED` du modèle (`src/views/chronology/E049.js:104`) : il ne se recalcule pas tout seul si un futur collègne introduit un appel. La garde est donc la relecture + la commande de vérification finale.
- **Effort** : S.
- **Vérification** : `grep -Ec` sur les noms d'API proscrites dans `E067.js` → `0` ; lecture de `E067.js:227` et `:240` → zéro appel annoncé et attribut `data-e067-raw="0"`.

## E067-02 — Assemblage hors flux puis greffe structurelle unique

- **Problème / preuve** : sans point de greffe unique, chaque ajout de ligne dans le panneau (`E067.js:304-320` crée dix paires de définitions) pourrait devenir une insertion séparée, avec autant de reflows et un risque d'état intermédiaire visible. Le stub (`E067.js:1-4`) ne définissait aucun ordre d'assemblage. Le modèle de passe 1 montre la discipline contraire : un `register` unique et un `ctx.css` unique (`src/views/chronology/E049.js:190`, `:237`), mais il ne borne pas le nombre d'écritures structurelles du greffon.
- **Solution** : `E067.js:163-168` concentre toute la greffe du panneau dans `graftPanel()` : un seul appel à `replaceChildren(...children)` (`:166`), appelé une seule fois en `:325` avec les six enfants `title, lede, list, demo, bilan, renders` construits hors flux en `:298-320`. Le compteur `panelGrafts` (`:122`, `:167`) est affiché en `:228` et publié en `:241`.
- **Impact** : le sous-arbre complet est remplacé en une opération atomique : aucun état partiel, une seule écriture structurelle par rendu, lisible dans `#chronology-v2-e067-graft`.
- **Risque** : `panelGrafts` cumule les rendus successifs ; le libellé précise « une par rendu (N rendu(s)) » pour éviter de lire `N > 1` comme une anomalie. Le compteur n'est pas remis à zéro, ce qui est voulu pour l'audit de la session.
- **Effort** : S.
- **Vérification** : relecture — une seule définition de `graftPanel` (`:165`), un seul appel (`:325`), `replaceChildren` du panneau absent de `paint()` (`:213-251`) ; harnais — après un rendu, `data-e067-grafts` vaut `1`.

Le modèle de passe 1 s'appuie sur `textContent` dans sa fonction `write()` (`src/views/chronology/E049.js:125-127`) mais n'expose pas de chaîne témoin mesurable.
- **Solution** : `E067.js:49-52` définit la chaîne témoin ; `:178` la passe comme troisième argument de `ctx.el('span', 'v2e067-inert', SAMPLE)`, donc comme texte. `:218-219` relève le nombre d'enfants de ce nœud et l'égalité exacte de son `textContent` avec la source ; `:229` affiche le résultat dans `#chronology-v2-e067-inert` et `:242` publie `data-e067-inert`.
- **Impact** : `0 élément créé`, `texte conservé à l'identique : oui`, et la longueur de la chaîne (mesurée, non codée en dur) est indiquée : l'échappement est démontré, pas promis.
- **Risque** : le nœud témoin est recréé à chaque écriture du conteneur de démonstration (`:333`) ; c'est précisément ce qui vérifie que l'inertie est une propriété de la construction par nœuds, et non de la persistance d'un ancien nœud. Aucune région live n'est utilisée pour annoncer ce résultat.
- **Effort** : S.

## E067-04 — Détachement effectif de l'ancien sous-arbre

- **Problème / preuve** : remplacer le contenu d'un conteneur par une chaîne peut laisser des références anciennes connectées ailleurs ou produire des nœuds fantômes. Le stub (`E067.js:1-4`) ne démontrait aucun détachement. Le modèle de passe 1 note que la coque détruit le stage (`src/views/chronology/E049.js:133-137`) mais ne mesure pas l'état `isConnected` des nœuds remplacés.
- **Solution** : `E067.js:170-180` construit les enfants du conteneur de démonstration ; `:329-334` l'écrit deux fois de suite, en conservant la première référence dans `demoFirst` (`:332`). `:220-221` mesure `demoFirst.isConnected === false` et la présence d'un remplaçant portant le même identifiant ; `:230` l'affiche dans `#chronology-v2-e067-detach` et `:243` publie `data-e067-detached`. Le style du conteneur et de ses enfants est défini en `:103-108`.
- **Impact** : l'ancien nœud est bien détaché, le nœud neuf est présent, et les deux écritures de démonstration sont comptées : la différence entre « ancien » et « remplaçant » est observable dans le DOM et lisible en texte.
- **Risque** : l'identifiant `chronology-v2-e067-demo-child` est volontairement réutilisé par le nœud neuf (`:177`) : l'ancien porteur étant détaché, il n'y a pas de doublon dans le document — c'est précisément l'objet du chantier E067-05. Les deux écritures ont lieu pendant l'installation, jamais pendant un rafraîchissement.
- **Effort** : S.
- **Vérification** : harnais — la référence conservée par `demoFirst` répond `isConnected === false` après `:333` ; `#chronology-v2-e067-demo > span:first-child.id` vaut `chronology-v2-e067-demo-child` ; libellé « ancien nœud détaché : oui · remplaçant présent : oui ».

## E067-05 — Unicité des identifiants dans le sous-arbre réécrit

- **Problème / preuve** : une écriture par concaténation de balisage peut dupliquer un identifiant si l'ancien contenu n'est pas détaché ; le registre rejoue les greffons (`UNIFIED_AUDIT/CHRONOLOGIE/views/E049.md`, chantier E049-10 : `registry.js:39-42`) et le risque se propage. Le stub (`E067.js:1-4`) ne déclarait aucun identifiant. Le modèle de passe 1 liste ses propres identifiants en `:27-37` mais ne les audite pas à l'exécution.

- **Risque** : l'audit est circonscrit au panneau et à son sous-arbre ; le nœud témoin hors panneau (E067-06) est préfixé lui aussi (`:46`) mais relève de la garde `ensureNode`, pas de cet audit. Le décompte inclut le panneau lui-même dans les nœuds examinés (`:185`).

## E067-06 — Préservation des nœuds extérieurs au conteneur réécrit

- **Problème / preuve** : un remplacement trop large (tout le `innerHTML` du parent, ou une recreation du panneau lui-même) emporterait les contrôles voisins et casserait les références détenues par la coque. Le stub (`E067.js:1-4`) ne délimitait aucune frontière de réécriture. Le modèle de passe 1 souligne que la coque vide le stage (`src/views/chronology/E049.js:133-137`) et que les nœuds détachés doivent être réattachés, non clonés (`:134-146`).
- **Solution** : `E067.js:289-292` crée un nœud témoin `<p id="chronology-v2-e067-sentinel">` frère du panneau dans l'hôte, via `ensureNode` (`:134-146`) qui le réattache au parent courant sans le cloner. `:222` vérifie qu'il reste connecté et que son parent est le même que celui du panneau ; `:232` affiche « intact : oui », `:245` publie `data-e067-sentinel`. Sa mise en forme est en `:79-82`.
- **Impact** : la frontière de la réécriture est prouvée : `panel.replaceChildren()` (`:166`) ne touche qu'aux enfants du panneau, jamais au frère, dont l'identité JavaScript survit aux rendus successifs.
- **Risque** : le témoin est un nœud inoffensif sans `tabindex` et sans rôle : il n'ajoute aucun arrêt de tabulation ni annonce. Si la coque remplace l'hôte entier, `ensureNode` retrouve le nœud détaché par `getElementById` (`:139`) ; si le document est rechargé, un nœud neuf est créé, ce qui est le comportement attendu.
- **Effort** : S.
- **Vérification** : harnais — `sentinel.isConnected === true` et `sentinel.parentElement === panel.parentElement` après deux rendus ; lecture de `E067.js:166` — aucun remplacement de l'hôte.

## E067-07 — Aucun parseur de balisage, aucun fragment contextuel

- **Problème / preuve** : même sans écrire de chaîne dans le DOM, une lentille pourrait analyser une chaîne avec un parseur puis insérer le fragment obtenu, réintroduisant le coût de parsing et le risque d'injection. Le stub (`E067.js:1-4`) n'interdisait rien. Le modèle de passe 1 n'invoque aucun parseur mais ne l'affiche pas explicitement ; seul son `write()` (`src/views/chronology/E049.js:125-127`) montre la voie textuelle.
- **Solution** : `E067.js:62-65` assemble les deux noms d'API de parseur par concaténation ; `:70` porte le constat `parseur: 0` ; `:233` affiche `DOMParser · createContextualFragment : 0 recours` dans `#chronology-v2-e067-parser` et `:246` publie `data-e067-parser="0"`.
- **Impact** : aucun octet de balisage n'est analysé par le module : la structure provient exclusivement de `ctx.el` (`:141`, `:174`, `:178`, `:272-273`, `:298-320`) et des greffes de nœuds (`:166`, `:330`, `:333`).
- **Risque** : la distinction avec E067-01 est nette : E067-01 interdit l'écriture directe d'une chaîne, E067-07 interdit l'analyse préalable d'une chaîne suivie d'une insertion de fragment. Les deux constats sont affichés dans deux lignes distinctes du `<dl>` (`:304`, `:310`).
- **Effort** : S.
- **Vérification** : relecture — aucune occurrence littérale des deux API dans le fichier ; `#chronology-v2-e067-parser` affiche `0 recours` ; les seules créations de nœuds passent par `make(...)` (`:272-273`, `:298-320`).

## E067-08 — Rafraîchissement par texte, sans nouvelle greffe structurelle

- **Problème / preuve** : une vue reconstruite à chaque rendu expose dix libellés (`:304-313`) à une tentation de réécriture complète ; le modèle de passe 1 rappelle le rejeu des greffons (`UNIFIED_AUDIT/CHRONOLOGIE/views/E049.md`, E049-10 : `registry.js:39-42`) et l'isolement de leurs erreurs (`:39-42`). Le stub (`E067.js:1-4`) ne définissait aucune politique de mise à jour.
- **Solution** : `E067.js:148-157` centralise les mises à jour dans `write()`, qui ne touche à `textContent` que si la valeur diffère et incrémente `textWrites`. `:225` calcule `extraGrafts = panelGrafts - installs` ; `:234` affiche le nombre d'écritures de texte et le nombre de greffes supplémentaires dans `#chronology-v2-e067-refresh`, `:247` publie `data-e067-extra-grafts`. `paint()` est appelé deux fois (`:341`, `:346`) ; la seconde suit `bindMedia()` (`:253-269`) : un changement réel de préférence système déclenche un rafraîchissement sans toucher à la structure. `ensureNode` (`:134-146`) protège la réutilisation du panneau entre rendus, et `register` reste unique (`:349-351`).
- **Impact** : `greffes structurelles supplémentaires après la première : 0` est vérifiable après un changement d'état ; la vue reste stable tandis que les seuls chiffres qui changent sont des textes de `<dd>`.
- **Risque** : l'écouteur `change` est le seul du module, posé sous la garde `mediaBound` (`:125`, `:257`, `:267`) : pas de sondage, pas de minuteur, pas de fuite sur les rendus successifs. Le compteur `textWrites` ne mesure que les écritures effectivement différentes, pas les appels à `write()`. Ce chantier ne recouvre pas E066 (signature anti-écriture redondante) : il garantit l'absence de réécriture structurelle, pas l'existence d'une signature.
- **Effort** : M.
- **Vérification** : harnais — émuler un changement de `(prefers-reduced-motion: reduce)` → `textWrites` augmente, `extraGrafts` reste `0`, `data-e067-grafts` reste `1` pour un rendu donné ; relecture — `replaceChildren` du panneau uniquement en `:166`.

## Statut d'implémentation

Les dix chantiers E067-01 à E067-10 sont implémentés dans `src/views/chronology/v2/E067.js` uniquement, soit 351 lignes relues. Une seule feuille CSS est injectée via `ctx.css('chronology-v2-e067', CSS)` (`E067.js:76-119`, appel en `:284`). Dix-huit identifiants DOM préfixés `chronology-v2-e067-` (`:29-46`) sont protégés par `ensureNode` (`:134-146`) et réutilisés d'un rendu à l'autre ; `panel.replaceChildren()` n'est appelé qu'en `:166`, une fois par rendu. Un seul `register('E067', ctx => { … })` (`:349-351`) et un seul import de registre (`:1`). Aucun fichier partagé n'est modifié, aucun sélecteur existant n'est renommé, aucune donnée n'est inventée, aucune région live n'est ajoutée, aucun mouvement n'est créé.

## Blocages / limites inter-domaines

- Les constats « zéro écriture de balisage brut » (E067-01), « zéro parseur » (E067-07) et « zéro style en chaîne » (E067-09) sont des faits structurels vérifiés par relecture et affichés comme tels (`:70`) : le module ne peut pas analyser son propre code source à l'exécution sans réseau ni lecture de fichier, ce qui est interdit par le contrat. La garde effective est donc la relecture + `node --check` + les recherches statiques du tableau final.
- L'hôte `atlas-chrono-main` (`:47`, `:286`) est supposé présent, comme dans le modèle de passe 1 ; à défaut, le greffon retombe sur `ctx.stage` puis `ctx.layout` (`:286`). Aucun sélecteur d'hôte n'est modifié, donc aucun impact sur la coque.
- La frontière avec E066 (signature anti-écriture redondante) et E068 (idempotence multi-rendus) est maintenue : `write()` (`:151-157`) déduplique les écritures pour éviter le bruit, mais ne calcule aucune signature ; `ensureNode` (`:134-146`) réutilise les nœuds, mais ne porte pas le contrat général d'idempotence de la lentille E068. Un maître d'œuvre souhaitant centraliser ces invariants doit le faire dans ces lentilles, pas ici.
