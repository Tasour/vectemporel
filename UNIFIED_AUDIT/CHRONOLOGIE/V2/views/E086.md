## E086-01 — Contrat d'entrée du greffon non vérifié : échec silencieux possible

- **Problème / preuve** : `registry.js:28-37` fabrique l'API passée aux greffons (`css`, `el`, `reducedMotion`) en étalant `ctx`, puis `registry.js:39-42` applique chaque greffon dans un `try/catch` qui neutralise les erreurs (`:41`). Rien ne garantit en amont que `viewId`, `stage` et `layout` existent ni que les helpers soient des fonctions. Le stub initial (quatre lignes utiles) n'exerçait aucun contrôle : un greffon présupposant le contrat pouvait être neutralisé sans que l'utilisateur ne voie rien.
- **Solution** : `E086.js:160-166` vérifie `viewId === 'chronologyv2'`, la présence de `stage` et `layout`, et le type des trois helpers ; `:185` publie le résultat ; `:208` ajoute une garde défensive avant tout travail ; `:211-212` ne compte le rendu que lorsque le contrat est exploitable.
- **Impact** : une dérive du contrat devient visible dans le panneau au lieu d'être absorbée par le registre, sans modifier `registry.js`.
- **Risque** : le contrôle décrit le contrat courant, il ne le répare pas. Si le registre change de nom de helper, la ligne passe en « À VÉRIFIER » et la relecture du module est nécessaire.
- **Effort** : S.
- **Vérification** : harnais — rendu nominal : ligne 01 « CONFORME », `data-e086-ok="10"` ; rendu avec `stage` absent : ligne 01 « À VÉRIFIER », `data-e086-warn ≥ 1`. `node --check` inchangé.

## E086-02 — Aucune mesure du nombre réel de feuilles CSS du greffon

- **Problème / preuve** : `registry.js:13-19` (`cssOnce`) protège l'insertion d'une feuille par son identifiant, et `registry.js:39-42` rejoue les greffons à chaque rendu. Le registre garantit l'unicité du `<style>` mais n'expose aucun compteur : une seconde feuille portant le même identifiant, introduite ailleurs, resterait invisible. Le stub initial n'injectait aucune feuille.
- **Solution** : `E086.js:22` fixe `CSS_ID`, `:53-114` définit l'unique chaîne CSS, `:212` est le seul appel d'injection ; `:168` compte les `<style id="chronology-v2-e086">` réels, `:186` écrit la ligne, `:254` publie `data-e086-css-count`, `:194` rappelle le compte dans le contrôle d'idempotence.
- **Impact** : l'unicité de la feuille devient une mesure observable et non une hypothèse sur le comportement du registre.
- **Risque** : le comptage porte sur le document entier ; une feuille homonyme injectée par un autre acteur déclencherait une alerte légitime mais hors du périmètre de cette lentille.
- **Effort** : S.
- **Vérification** : harnais — `1 feuille « chronology-v2-e086 » dans le document`, `data-e086-css-count="1"` ; relecture : une seule occurrence de l'appel d'injection (`E086.js:212`), un seul `CSS_ID` (`:22`).

## E086-03 — Identifiants du greffon : unicité non contrôlée après re-render

- **Problème / preuve** : `registry.js:21-26` crée les nœuds sans identifiant, `registry.js:39-42` rejoue les greffons, et le modèle de passe 1 documente la reconstruction du conteneur à chaque navigation (`E049.md:104`). Sans garde, deux rendus pouvaient laisser coexister deux nœuds portant le même ID, avec des sélecteurs CSS ambigus et un `getElementById` qui n'en voit qu'un.
- **Solution** : `E086.js:23-28` et `:34` énumèrent seize identifiants possédés (six de structure, dix de ligne) ; `:121-129` fournit `ensureNode` avec réutilisation et déplacement dans le parent courant ; `:169` vérifie que chaque ID apparaît exactement une fois, `:187` l'écrit, `:215` et `:232` utilisent la garde pour le panneau et les lignes.
- **Impact** : aucun doublon d'ID après navigation aller-retour ; le CSS reste adressable sans ambiguïté.
- **Risque** : un nœud retrouvé est déplacé, jamais cloné (`E086.js:127`) ; ses attributs sont réécrits à chaque rendu (`:251-258`), donc jamais périmés. Le contrôle couvre uniquement les seize ID possédés, pas ceux du reste de la vue.
- **Effort** : M.
- **Vérification** : harnais — `16/16 identifiants uniques` au premier rendu ; deux rendus successifs → un seul `#chronology-v2-e086-audit`, un seul `<style>` ; relecture : aucune concaténation d'ID ailleurs que dans `OWNED_IDS` (`:35`).

## E086-04 — Espace de noms des identifiants : préfixation non prouvée

- **Problème / preuve** : `registry.js:9-11` accepte n'importe quelle chaîne comme identifiant de greffon et `registry.js:21-26` n'impose aucun préfixe aux nœuds créés. Le risque n'est pas ici la duplication (chantier 03) mais la collision avec un ID générique d'une autre lentille : un ID `check-01` non qualifié pourrait être retrouvé par un greffon voisin.
- **Solution** : `E086.js:30` déclare `PREFIX = 'chronology-v2-e086-'` ; `:34` en dérive les dix ID de ligne, `:23-28` porte le préfixe sur les six ID de structure ; `:170` teste la préfixation de chaque ID, `:179` publie `16/16 identifiants préfixés …` ; les sélecteurs CSS sont tous ancrés sur l'ID préfixé (`:54`, `:71-98`).
- **Impact** : l'appartenance de chaque nœud à la lentille est explicite et vérifiable, sans toucher au registre.
- **Risque** : le test est statique sur la liste déclarée (`:35`) ; un futur nœud créé sans passer par `CHECK_IDS` ou `OWNED_IDS` échapperait au contrôle — d'où la consigne de dériver tout nouvel ID du `PREFIX`.
- **Effort** : S.
- **Vérification** : relecture — zéro ID littéral non préfixé dans `E086.js` ; harnais — ligne 04 « CONFORME · 16/16 identifiants préfixés chronology-v2-e086- ».

## E086-05 — Feuille CSS injectée sans filtre d'hygiène

- **Problème / preuve** : `registry.js:13-19` recopie `rules` textuellement dans `style.textContent` (`:17`) sans filtrer son contenu. Une priorité forcée, un import distant, une URL réseau ou un panneau à position fixe dans la feuille d'une lentille auraient franchi ce point sans contrôle, alors que le cahier des charges V2 impose zéro réseau et un bloc en flux (`E049.md:98` décrit le même arbitrage pour le panneau E049).
- **Solution** : `E086.js:53-114` est une feuille sans directive interdite, en blocs en flux et avec replis `620px` (`:100-102`), `prefers-reduced-motion` (`:103-105`) et `forced-colors` (`:106-113`) ; `:171-172` applique à cette même chaîne `CSS` un filtre sur les directives proscrites ; `:180` publie le résultat ; `:50-52` documente l'intention.
- **Impact** : la règle d'hygiène est autovérifiée au moment de l'injection, pas seulement relue à la main.
- **Risque** : le filtre ne porte que sur la chaîne possédée ; il ne contrôle ni `styles.css` ni les feuilles des autres lentilles. Un motif légitime ressemblant à une URL distante dans une future règle exigerait de réviser le filtre.
- **Effort** : M.
- **Vérification** : relecture croisée `E086.js:53-114` ↔ filtre `:171-172` ; harnais — ligne 05 « aucune priorité forcée, import, URL distante ou position fixe » ; recherche de motifs distants dans la feuille injectée : aucun résultat.

## E086-06 — Ressources actives distantes non détectées

- **Problème / preuve** : `registry.js:28-37` fournit les helpers sans inspecter le document, et `registry.js:39-42` ne vérifie rien après coup. Le modèle de passe 1 pose l'invariant « zéro réseau » comme exigence de qualité (`E049.md:4`), mais aucun mécanisme ne signale une ressource active distante apparue dans le DOM au fil des rendus.
- **Solution** : `E086.js:173-177` assemble les sélecteurs d'images, scripts, iframes et feuilles de style distantes à partir des schémas ; `:190` écrit le nombre trouvé ; `:191` vérifie séparément la structure sémantique. Les schémas sont assemblés (`:173`) plutôt qu'écrits littéralement, pour ne pas introduire d'URL distante dans le module lui-même.
- **Impact** : toute dérive « zéro réseau » devient mesurable dans le panneau sans intercepter la charge d'une page.
- **Risque** : seules les ressources *actives* chargées par le navigateur sont comptées ; un simple lien de citation `href` externe, autorisé par ailleurs, n'est pas un chargement et n'est donc pas signalé. Le contrôle est instantané, pas continu : aucun observateur n'est installé.
- **Effort** : M.
- **Vérification** : harnais — ligne 06 « 0 ressource active distante dans le document » ; contrôle statique du module : zéro appel réseau, zéro `XHR`, zéro URL distante littérale.

## E086-07 — Structure sémantique (main / h1) non vérifiée

- **Problème / preuve** : `registry.js:28-37` transmet `layout` sans garantir la présence d'un `<main>` unique ni d'un `<h1>` ; `registry.js:21-26` peut créer n'importe quelle balise. Une lentille qui ajouterait un second `<main>` ou un titre de niveau 1 concurrent dégraderait l'indexation et l'ordre de lecture, sans qu'aucun contrôle du registre ne le signale.
- **Solution** : `E086.js:178-179` compte `<main>` et `<h1>` dans le document, `:191` publie le résultat ; `:219` crée volontairement un `<h2>` pour le titre du panneau et `:216` une liste ordonnée, afin de ne pas concurrencer le titre principal ; `:217` relie le panneau à ce titre par `aria-labelledby`.
- **Impact** : la structure sémantique de la vue devient auditable et le panneau ne l'altère pas.
- **Risque** : le comptage est global au document. Si une autre lentille introduit un second `<main>`, l'alerte est juste mais sa correction relève du maître d'œuvre, pas de cette lentille. Le module n'écrit dans aucune région live, conformément au choix documenté en `E049.md:60-62`.
- **Effort** : S.
- **Vérification** : harnais — ligne 07 « 1 élément &lt;main&gt; · 1 titre(s) &lt;h1&gt; » ; relecture — un seul `make('h2', …)` (`:219`), aucun `role="status"` ni `aria-live` dans le module.

## E086-08 — État des contrôles non garanti hors couleur seule

- **Problème / preuve** : le CSS du panneau distingue les états par la couleur de bordure et de texte (`E086.js:78-98`), ce qui ne suffit pas : sans marqueur textuel et sans forme distincte, un daltonien ou une technologie d'assistance ne peut pas distinguer « CONFORME » de « À VÉRIFIER ». Le modèle de passe 1 pose la même exigence (« aucune info portée par la seule couleur », `E049.md:117-123`).
- **Solution** : `E086.js:148-155` centralise l'écriture : `appliquer` pose toujours `data-e086-state` et le libellé `[v] CONFORME` ou `[!] À VÉRIFIER` ensemble ; `:198-205` (`secondePasse`) relit le DOM *après* écriture et vérifie les dix lignes ; `:240-245` applique les neuf premiers contrôles, puis recalcule et réapplique le huitième. Le CSS ajoute bordure pleine contre bordure en pointillés (`:78-83`) et soulignement pointillé (`:93-98`), avec repli `forced-colors` (`:106-113`).
- **Impact** : l'état de chaque contrôle est lisible par le texte, par la forme et par l'attribut, sans dépendre de la teinte.
- **Risque** : le contrôle est auto-référentiel par construction : il garantit la cohérence interne du panneau, pas le contraste mesuré des couleurs — celui-ci reste à auditer par un outil dédié (limite inter-domaines).
- **Effort** : M.
- **Vérification** : harnais — ligne 08 « 10/10 lignes avec état textuel et marqueur », dix `data-e086-state` présents ; relecture — l'ordre `:240-245` garantit que `secondePasse` s'exécute après la première écriture.

## E086-09 — Préférence de mouvement réduit non publiée

- **Problème / preuve** : `registry.js:33-36` expose `reducedMotion` via `matchMedia` dans un `try/catch`, mais ni le registre ni le stub initial ne publient l'état de la préférence. Le modèle de passe 1 traite le même sujet (`E049.md:93-100`) et rappelle que la vue ne dispose pas d'indicateur propre.
- **Solution** : `E086.js:180-181` lit le helper et exige la présence du repli CSS ; `:103-105` neutralise l'unique transition du panneau en `prefers-reduced-motion` ; `:193` décrit l'état dans la ligne, `:248` le répète dans le bilan, `:258` publie `data-e086-reduced`. Aucune animation n'est créée ailleurs.
- **Impact** : la préférence est traçable et le peu de mouvement introduit par la lentille est neutralisé.
- **Risque** : si `matchMedia` lève une exception, le registre renvoie `false` (`registry.js:35`) : la ligne indique « mouvement réduit : non » alors que le réglage système peut être actif. Ce repli est hérité du contrat, non modifiable ici.
- **Effort** : S.
- **Vérification** : relecture — un seul `transition` dans la feuille (`:91`), neutralisé (`:104`) ; harnais — `data-e086-reduced="0"` avec le helper à `false`, bascule à `true` → libellé « oui » et ligne 09 toujours conforme.

## E086-10 — Idempotence multi-rendus non démontrée

- **Problème / preuve** : `registry.js:39-42` rejoue tous les greffons à chaque rendu et `registry.js:13-19` ne protège que l'unicité du style ; le modèle de passe 1 documente précisément ce scénario (`E049.md:102-109`). Le stub initial, sans nœud ni état, ne pouvait pas prouver qu'il restait un seul panneau après navigation.
- **Solution** : `E086.js:116` maintient un compteur de rendus module ; `:207-208` borne l'entrée, `:211` l'incrémente ; `:214-215` réutilise le panneau via `ensureNode` ; `:237-238` remplace les enfants plutôt que de les accumuler ; `:182` et `:194` comparent panneaux, feuilles et rendus ; `:251-252` publient `data-e086-renders`, `data-e086-ok` et `data-e086-warn`.
- **Impact** : un rendu répété ne crée ni doublon de panneau, ni fuite de nœud, et le bilan reste exact.
- **Risque** : le compteur survit aux rendus mais est réinitialisé au rechargement complet de la page ; c'est le comportement attendu d'un greffon sans état persistant. Le registre neutraliserait silencieusement une erreur (`registry.js:41`) : `node --check` et le harnais restent la première ligne de défense.
- **Effort** : M.
- **Vérification** : harnais — deux exécutions du greffon → un seul panneau, une seule feuille, `data-e086-renders="2"` et `rendus : 2 · panneaux : 1 · feuilles : 1` ; `node --check src/views/chronology/v2/E086.js` → PASS.

## Statut d'implémentation

Les dix chantiers E086-01 à E086-10 sont implémentés dans `src/views/chronology/v2/E086.js` uniquement, conformément au thème `themes.json[E086]`. Le panneau `#chronology-v2-e086-audit` affiche dix lignes indépendantes, chacune avec un libellé de résultat et un attribut `data-e086-state` ; seize identifiants tous préfixés `chronology-v2-e086-` sont protégés par `ensureNode` (`E086.js:118-129`). Une seule feuille CSS est injectée (`:53-114`, appel unique `:212`), un seul enregistrement du greffon est déclaré (`:207`), aucun fichier partagé n'est touché. Le harnais de relecture obtient `10/10 contrôles conformes` et confirme l'idempotence après deux rendus (un panneau, une feuille). Zéro réseau, zéro journalisation, zéro aléa, zéro HTML brut, zéro timer, zéro animation, zéro région live ajoutée.

## Blocages / limites inter-domaines

- `registry.js` (`:9-11`, `:13-19`, `:28-42`) et `index.js` ne sont pas modifiables : la lentille ne peut pas durcir le contrat d'entrée, filtrer les feuilles CSS des autres greffons ni empêcher le `try/catch` qui neutralise silencieusement une erreur.
- Les contrôles E086-06 et E086-07 sont des instantanés : sans observateur ni timer, ils ne détectent pas une ressource distante ou un second `<main>` apparu entre deux rendus. Une surveillance continue relèverait d'une lentille dédiée du domaine G.
- E086-08 valide la cohérence interne du panneau, pas le contraste réel des couleurs ni le rendu sous `forced-colors` : la mesure de contraste relève du domaine E (E047) et la relecture visuelle des captures du domaine H.
- Le contrôle de structure (E086-07) porte sur le document entier : une anomalie causée par une autre lentille serait signalée ici mais ne pourrait pas être corrigée dans ce module.
- Le repli de `reducedMotion` (`registry.js:33-36`) renvoie `false` si `matchMedia` échoue ; la lentille ne peut pas distinguer ce cas d'une préférence réellement absente.
- Aucune synthèse n'est produite : ce rapport ne fait que documenter ses dix chantiers, conformément à la consigne de périmètre.
