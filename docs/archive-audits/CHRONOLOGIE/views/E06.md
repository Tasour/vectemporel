# E06 — États et annonces (chronologie)

> Sources lues : `src/views/chronology.js`, `src/views/chronology/{registry,index}.js`,
> `src/views/_diagnostics.js`, `UNIFIED_AUDIT/CHRONOLOGIE/README.md`,
> `UNIFIED_AUDIT/views/atlas-chronologie.md`, `UNIFIED_AUDIT/MONDE/views/M38.md`.
> Aucun autre fichier fonctionnel modifié. Zéro réseau, zéro `Math.random`,
> zéro `console.*`, aucune donnée historique inventée.

> **Alias de chargement.** Le registre global importe `E006.js` (indice à trois
> chiffres). Ce fichier est réduit à `import './E06.js';` afin que la lentille
> canonique `E06` soit effectivement appliquée au rendu sans second
> `register()`. Les deux fichiers passent `node --check`.

## Thèse

La coque reconstruit intégralement le DOM de la chronologie à chaque
changement de store (`shell.js:137` via `store.js`), si bien qu'un état lu une
fois devient périmé dès le rendu suivant. `chronology.js` gère déjà trois
mécanismes distincts — le texte visible `#atlas-chrono-status`, la progression
`#nav-c2a-progress` et la région live `#nav-c2a-live` du C2 — mais plusieurs
transitions restent silencieuses (sélection d'un repère, états vides autres que
le filtre, atteinte d'une borne) et aucun miroir textuel ne permet de vérifier
après coup qu'un état a bien été annoncé une seule fois. E06 comble ce vide
dans le seul fichier de la lentille : un snapshot dérivé du rendu, comparé
entre deux `apply()`, une annonce priorisée par région live existante, et un
panneau de diagnostic horodaté par un compteur déterministe.

<a id="e06-01"></a>
## E06-01 — Snapshot d'état dérivé du DOM, source unique

- **Problème (preuve).** `chronology.js:16-17` conserve `local = { query, tag }`
  et `focusIntent` ; `chronology.js:233-236` recalcule `eraIndex` / `eventIndex`
  depuis le store partagé. Importer ces deux sources dans la lentille
  dupliquerait l'état et risquerait de l'écrire avant le rendu.
- **Solution concrète.** `readState(ctx)` lit exclusivement ce que
  `renderChronology()` a déjà produit : `data-country-id` du layout, bande
  `.era-band[aria-current="true"]` (nom), carte `.event-card[aria-current="true"]`
  (titre et `data-event-id`), `#atlas-chrono-search`.value, puce
  `[aria-pressed="true"]`, `#atlas-chrono-status`, nombre de `<li id^="event-">`,
  `disabled` des boutons d'action et identifiants `nav-c2a-empty-*`.
- **Impact sur l'évidence.** Le diagnostic reflète exactement ce que voit
  l'utilisateur ; aucune valeur n'est recalculée à partir d'une formule
  concurrente, aucun chiffre n'est inventé.
- **Risque.** `aria-current="location"` du fil C2 (`chronology.js:162`) ne doit
  pas être confondu avec l'ère courante : la lecture cible `.era-band` uniquement.
- **Effort.** S.
- **Vérification.** Le panneau `#e06-state-panel` affiche un pays, une ère et un
  repère non « — » dès qu'une carte est sélectionnée.

<a id="e06-02"></a>
## E06-02 — Annonce du repère sélectionné

- **Problème (preuve).** `navSay()` est appelé sur le clic d'une ère
  (`chronology.js:301`) et sur le filtrage (`chronology.js:324,340,368,454`),
  mais pas sur le clic d'une carte (`chronology.js:406-409`) ni sur les boutons
  précédent/suivant (`chronology.js:515-524`) : le changement de rang global
  reste silencieux pour un lecteur d'écran.
- **Solution concrète.** Comparer `eventId` entre deux rendus. En cas de
  changement, écrire une seule phrase dans la région live existante :
  « Repère sélectionné : *titre*, rang *i/n* dans l'ère *nom*. » L'annonce est
  dédupliquée par égalité stricte du message.
- **Impact sur l'évidence.** Le parcours clavier `←`/`→` et les clics de cartes
  produisent la même information vocalisée que le clic sur une ère.
- **Risque.** `navSay()` peut écrire juste avant dans la même région. Celle-ci
  étant `aria-atomic="true"`, seul le dernier message — ici complet — est lu ;
  aucun doublon de région n'est créé (E06-07).
- **Effort.** M.
- **Vérification.** Sélectionner une carte : le texte de `#nav-c2a-live` contient
  le titre de cette carte et « rang » ; cliquer deux fois sans changement
  n'incrémente pas le compteur d'annonces.

<a id="e06-03"></a>
## E06-03 — Annonce des états vides

- **Problème (preuve).** `chronology.js:353-373,468-471,527-535` crée cinq états
  vides (`nav-c2a-empty-filter`, `-era`, `-points`, `-event`, `-kicker`) mais
  seul le filtre est annoncé, via `announceFilter()` (`chronology.js:190-195`).
  Une ère sans repère, un repère sans point ou une fiche vide restent muets.
- **Solution concrète.** Détecter la présence de l'un des quatre ids porteurs de
  message et émettre le texte déjà affiché dans la vue, sans rédaction
  supplémentaire : « Aucun repère documenté pour cette ère. », « Aucun point
  documenté pour ce repère. », « Aucun repère sélectionné… ». Le cas `-kicker`
  est ignoré au profit de `-event`, qui porte l'explication. Priorité inférieure
  à E06-02, supérieure à E06-04.
- **Impact sur l'évidence.** Un état vide est compris au même titre qu'un état
  rempli, sans ajouter de fait historique.
- **Risque.** L'annonce est conditionnée à un *changement* d'état vide : un
  rendu sans transition ne répète pas le message.
- **Effort.** S.
- **Vérification.** Forcer une ère sans repère : la région live contient le
  message d'ère vide et le compteur d'annonces augmente d'un.

<a id="e06-04"></a>
## E06-04 — Miroir live des compteurs et du filtre

- **Problème (preuve).** `#atlas-chrono-status` (`chronology.js:247-256`) et
  `#nav-c2a-progress` (`chronology.js:263-268`) portent les trois échelles
  « ère k/N · repère j/m · rang global i/n ». Le commentaire
  `chronology.js:244-246` explique leur absence de `role="status"` pour éviter
  les doublons : ils ne sont donc jamais vocalisés tels quels.
- **Solution concrète.** Si aucun événement prioritaire n'a été détecté, comparer
  le texte du statut entre deux rendus et le reprendre mot pour mot dans la
  région live, avec le préfixe `Filtre (query|tag|both) :` quand un filtre est
  actif. Une seule écriture par rendu, dédupliquée (E06-02 > E06-03 > E06-06 >
  E06-04).
- **Impact sur l'évidence.** Les compteurs deviennent auditables à l'oral sans
  créer de seconde région live.
- **Risque.** Bavardage pendant la saisie : la déduplication stricte et la
  priorité de E06-02/E06-03 limitent le flux à une phrase par frappe significative.
- **Effort.** M.
- **Vérification.** Saisir un terme dans `#atlas-chrono-search` : la région live
  contient le texte du statut préfixé `Filtre (query) :`; vider le champ :
  message de retour au périmètre d'ère.

<a id="e06-05"></a>
## E06-05 — Cohérence `aria-current` ↔ `is-active`

- **Problème (preuve).** `chronology.js:284,290` et `chronology.js:385,390`
  écrivent `is-active` et `aria-current="true"` dans le même branchement. Une
  lentille concurrente ou un rendu partiel pourrait désynchroniser les deux,
  rendant l'état actif porté par la seule couleur (`styles.css:144`,
  `chronology.js:62`).
- **Solution concrète.** `reconcileCurrent()` parcourt uniquement
  `.era-band, .event-card` : pose `aria-current="true"` si `is-active` est
  présent, le retire sinon, et expose `data-e06-state="active|idle"`. Les puces
  de thèmes (`aria-pressed`) et le fil C2 (`aria-current="location"`) ne sont
  pas touchés.
- **Impact sur l'évidence.** L'état courant reste sémantique même après une
  modification visuelle externe ; cohérence avec ATLAS-CHRONO-02/-03.
- **Risque.** Aucune écriture sur un nœud détaché : le parcours part de
  `ctx.layout` au rendu courant.
- **Effort.** S.
- **Vérification.** Ajouter `is-active` à une carte inactive : au rendu suivant,
  `aria-current="true"` et `data-e06-state="active"` apparaissent ensemble.

<a id="e06-06"></a>
## E06-06 — Bornes : état annoncé, pas seulement `disabled`

- **Problème (preuve).** `chronology.js:513-514` désactive « précédent » au rang 0
  et « suivant » au dernier rang. La borne est portée par la sémantique native
  de `disabled` et par le style, sans explication textuelle ni changement
  annoncé au moment où l'on atteint la fin de la chronologie.
- **Solution concrète.** Dériver `bound = start | end | none` de l'état des deux
  boutons ; annoncer « Début de la chronologie : aucun repère précédent. » ou
  « Fin de la chronologie : aucun repère suivant. » uniquement lors du
  *franchissement* (`before.bound !== after.bound`). Exposer la valeur en
  `data-e06-bound` sur le layout.
- **Impact sur l'évidence.** L'utilisateur comprend pourquoi le bouton ne répond
  plus ; le compteur d'annonces prouve l'événement.
- **Risque.** Aucun `preventDefault`, aucun clic synthétique, aucun appel à
  `selectEvent` depuis la lentille : `store.js` reste la seule source de vérité.
- **Effort.** S.
- **Vérification.** Aller au dernier repère avec `→` : la région live contient
  « Fin de la chronologie » et `data-e06-bound="end"`.

<a id="e06-07"></a>
## E06-07 — Région live unique, repli déterministe, trace bornée

- **Problème (preuve).** `chronology.js:119-138` crée `#nav-c2a-live` dans
  `<body>` pour survivre au `innerHTML` de la coque. Créer une seconde région
  concurrente produirait des annonces doubles ; si cette région disparaît, plus
  rien n'est vocalisé.
- **Solution concrète.** `ensureLive()` réutilise `#nav-c2a-live` si elle est
  connectée, sinon `#e06-live-fallback`, sinon crée un `<p>` sr-only
  `role="status" aria-live="polite" aria-atomic="true"` dans `<body>`. Chaque
  message est conservé dans une file bornée à 8 entrées, préfixé d'un compteur
  séquentiel (`sequence`), sans `Date.now()` ni `Math.random()`.
- **Impact sur l'évidence.** Une seule annonce par action, retraçable et
  reproductible d'une exécution à l'autre.
- **Risque.** Un nœud présent mais déconnecté est écarté par `isConnected`,
  évitant d'écrire dans un fantôme de rendu précédent.
- **Effort.** M.
- **Vérification.** Après dix changements d'état : un seul élément live dans le
  document, `#e06-announce-trace` contient exactement huit `<li>` numérotés
  3 … 10 (les deux premiers ayant été évincés).

<a id="e06-08"></a>
## E06-08 — État de filtre exposé en attributs

- **Problème (preuve).** `local.query` et `local.tag` ne sont pas exposés dans
  le DOM ; `aria-pressed` des puces (`chronology.js:334,449`) porte l'état
  d'une bascule mais le compteur `atlas-chrono-count` (`chronology.js:344`) n'est
  relié à aucune région live dédiée.
- **Solution concrète.** Poser sur le layout `data-e06-filter` = `none | query |
  tag | both`, `data-e06-matches` = nombre de cartes visibles et
  `data-e06-bound`, tous dérivés du rendu (lecture de `.value` et des attributs
  ARIA, aucune écriture dans le champ). Le libellé `Filtre (…)` de E06-04 utilise
  la même valeur.
- **Impact sur l'évidence.** Un outil externe peut interroger l'état du filtre
  sans import du store ; cohérence avec ATLAS-CHRONO-09 (`data-*` réels).
- **Risque.** Les ids et sélecteurs de test (`#atlas-chrono-search`,
  `.event-card`) restent inchangés ; aucun `aria-pressed` n'est réécrit.
- **Effort.** S.
- **Vérification.** Saisir « esclavage » puis activer un thème :
  `data-e06-filter="both"` et `data-e06-matches` égal au nombre de cartes
  affichées.

<a id="e06-09"></a>
## E06-09 — Panneau de diagnostic des états et annonces

- **Problème (preuve).** `UNIFIED_AUDIT/CHRONOLOGIE/README.md` prévoit un
  rapport et un module par lentille, et `_diagnostics.js:69-79` regroupe les
  panneaux dont l'id suit le motif `eNN-…`. Sans panneau, la vérification
  « une seule annonce par changement » n'est pas rejouable après coup.
- **Solution concrète.** `<section id="e06-state-panel" role="group">` avec une
  `<dl>` de neuf champs (pays, ère, repère, rang, filtre, affichés, borne, état
  vide, annonces) et `<ol id="e06-announce-trace">`. Le panneau porte dès sa
  création `data-chronology-diagnostic` : il est masqué au premier rendu par la
  feuille déjà installée par `_diagnostics.js`, puis regroupé dans le tiroir
  « Diagnostics · 100 ».
- **Impact sur l'évidence.** La vérification est reproductible sans outil
  externe ni lecteur d'écran ; le tiroir existant reste le seul point d'entrée.
- **Risque.** Le marquage manuel court-circuite `originalParents` de
  `_diagnostics.js` : à la fermeture du tiroir, le repli documenté renvoie le
  panneau dans `stage` plutôt que dans `layout`. Aucun contenu n'est perdu.
- **Effort.** M.
- **Vérification.** Ouvrir « Diagnostics · 100 » : un seul `#e06-state-panel`,
  neuf `<dt>`, une trace de huit `<li>` maximum.

<a id="e06-10"></a>
## E06-10 — Garde-fous : idempotence, zéro aléa, `node --check`

- **Problème (preuve).** `registry.js:45-56` rejoue `apply(api)` à chaque rendu
  et neutralise une lentille défaillante. Un `MutationObserver` ou un
  `addEventListener` réattaché à chaque passe dupliquerait les annonces ; un
  `Math.random()` ou un horodatage rendrait la trace illisible d'une exécution
  à l'autre.
- **Solution concrète.** Toute la mémoire est dans des variables de module
  (`previous`, `lastMessage`, `sequence`, `fields`, `traceNode`) ; aucun
  observateur, aucun écouteur, aucune écriture dans le store. `ctx.css(
  'chronology-e06', …)` est injecté une seule fois par `cssOnce`
  (`registry.js:25-31`). Tous les ids sont préfixés `e06-` et uniques ; la
  recherche de `console|Math\.random|fetch|XMLHttpRequest` dans `E06.js`
  donne 0 occurrence. Le premier rendu n'annonce rien (`previous === null`).
- **Impact sur l'évidence.** La lentille est neutralisable sans casser le rendu ;
  `node --check` suffit à la validation statique demandée par la vague.
- **Risque.** L'alias `E006.js` importe `E06.js` une seule fois : l'ordre des
  imports de `index.js` est inchangé et aucun `register()` en double n'est
  produit (contrôle : `viewDiagnostics().entries` contient `E06` une fois).
- **Effort.** S.
- **Vérification.** `node --check src/views/chronology/E06.js` et
  `node --check src/views/chronology/E006.js` : **OK**.

## Synthèse des dépendances

- **E06-01 → E06-02 → E06-03 → E06-06 → E06-04** : le snapshot alimente une
  file de priorité ; un rendu produisant plusieurs changements ne génère
  qu'une phrase, la plus informative.
- **E06-05 ↔ E06-01** : la réparation de `aria-current` précède la lecture du
  snapshot, qui voit donc l'état déjà cohérent.
- **E06-07 ↔ E06-09** : la même file d'annonces sert la voix et la trace ; le
  compteur séquentiel remplace l'horodatage.
- **E06-08 ↔ E06-04** : `data-e06-filter` et le préfixe vocalisé dérivent de la
  même observation, sans seconde source de vérité.
- **E06-10** encadre les neuf autres par l'idempotence et l'absence d'effet de
  bord.

## Blocages de périmètre (documentés, non implémentés ici)

1. `chronology.js` : aucun appel `navSay()` n'est ajouté ni retiré ; la lentille
   se contente d'écrire dans la région live déjà créée par le C2.
2. `store.js` / `keyboard.js` : le routage clavier et la source de vérité
   restent inchangés (contrat `verify.mjs:21` : un seul `keydown`).
3. `_diagnostics.js` : le motif de marquage et le tiroir ne sont pas modifiés ;
   E06 s'y conforme par un id `e06-*` et un attribut explicite.
