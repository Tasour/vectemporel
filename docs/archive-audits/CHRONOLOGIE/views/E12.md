## E12-01 — Années en texte nu : aucun `<time datetime>` lisible par machine

- **Problème / preuve** : `src/views/chronology.js:26` formate les années en texte
  (`1789`, `44 av. J.-C.`) et les injecte tels quels dans `.event-year` (`:392`) et
  `.aside-year` (`:430`). Le `li` porte pourtant l'entier brut `data-year` (`:380`).
  Aucun `<time>` n'existe dans la vue : un parseur doit deviner qu'une chaîne
  « av. J.-C. » est une année négative.
- **Solution** : `isoYear()` convertit l'entier en année ISO 8601 étendue — `1789`
  ou `-0044` (paddé sur 4 chiffres) — et `makeTime()` enveloppe **le texte visible
  existant** dans un `<time datetime="…" data-sem-field="year">`. Le libellé
  français ne change pas ; la fiche réutilise l'année de la carte active lue dans
  le DOM, sans toucher au store.
- **Impact** : les repères et la fiche deviennent datables sans ambiguïté par un
  lecteur d'écran, un extracteur ou un futur export, pour un coût DOM nul.
- **Risque** : le jeu de données ne contient ni mois ni jour — le `datetime` est
  donc une **année**, pas une date civile complète ; le dictionnaire (E12-08) le
  dit explicitement. Aucune conversion de calendrier n'est tentée.
- **Effort** : M.
- **Vérification** : sur France, `3/3` `.event-year time[datetime]` et l'année de
  la fiche datée ; premier repère `datetime="-0600"` ; le texte visible « 600 av.
  J.-C. » reste inchangé.

## E12-02 — Ères : intervalle non typé, bornes non datées

- **Problème / preuve** : chaque bande porte `data-start` / `data-end` (`:288-289`)
  et un span `.atlas-chrono-era-range` contenant `formatYear(start) → formatYear(end)`
  (`:296`). Rien ne déclare qu'il s'agit d'un intervalle temporel : les deux bornes
  sont du texte, le sens de la flèche est purement visuel.
- **Solution** : `stampEraRanges()` pose `data-sem-type="era"`,
  `data-sem-start` / `data-sem-end` (ISO), et remplace les deux segments du texte
  par deux `<time>` (`data-sem-field="start"` / `"end"`) séparés par le même
  nœud texte ` → `. Le nom de l'ère et l'`aria-current` existants sont préservés.
- **Impact** : l'intervalle est lisible à la fois par l'humain et par la machine,
  sans changer une seule règle CSS de la vue.
- **Risque** : le découpage s'appuie sur le séparateur `' → '` produit par
  `chronology.js:296` ; si le séparateur change, la fonction renonce proprement
  (elle ne touche pas au nœud) plutôt que de produire un datetime faux.
- **Effort** : S.
- **Vérification** : `9/9` boutons d'ère typés et `18` `<time>` sur France, soit
  deux par ère ; paire échantillon `["-0600","476"]`.

## E12-03 — Aucun vocabulaire déclaré : les `data-*` n'ont pas de sens

- **Problème / preuve** : la vue émet `data-country-id` (`:215`), `data-era-id`,
  `data-event-id`, `data-importance` (`:382`), `data-kind` / `data-confidence`
  (`:477-478`) et `data-source-id` (`:495`). Ces attributs servent au filtrage et
  au style, mais aucun ne dit ce qu'il représente : un parseur ne peut pas
  distinguer un rang d'un score, ni une taxonomie d'un niveau de certitude.
- **Solution** : un vocabulaire local `vectemporel:chronology:1` est posé sur la
  racine (`data-sem-namespace`) puis décliné par `data-sem-type` sur les cinq
  entités présentes — `era`, `event`, `event-control`, `point`, `source` — et par
  `data-sem-role` sur les listes de sources. Le choix d'un identifiant **local**
  est délibéré : aucune URI `schema.org` distante, donc aucun chargement, même
  passif, dans un atlas hors ligne.
- **Impact** : chaque nœud porte son propre type ; les annotations peuvent être
  comptées, validées et réconciliées sans document externe.
- **Risque** : le vocabulaire n'est pas un standard — il est documenté dans le
  dictionnaire E12-08 et versionné dans la chaîne `…:1`, ce qui permet une
  migration ultérieure sans ambiguïté.
- **Effort** : M.
- **Vérification** : `[data-sem-namespace]` unique sur `.chronology-layout`,
  valeur `vectemporel:chronology:1` ; zéro occurrence de `http` dans le module.

## E12-04 — Type et confiance des points : tokens sans définition ni libellé

- **Problème / preuve** : `src/data/dataset.js` fournit quatre `kind`
  (`audit`, `figure`, `lieu`, `récit`) et quatre `confidence`
  (`certain`, `disputed`, `probable`, `vérifié`) ; la vue les affiche en texte
  uppercase via `styles.css:230` et porte `data-kind` / `data-confidence`. Le
  token `disputed` est anglais, et aucun libellé n'explique `audit` ou `vérifié`.
- **Solution** : deux tables figées `KIND_LABELS` et `CONFIDENCE_LABELS` fournissent
  le libellé français (`disputed` → « Contesté », `récit` → « Récit »). Chaque
  `li.point` reçoit `data-sem-kind-label` / `data-sem-confidence-label`, et les
  spans existants reçoivent un `title` (« Type : … », « Confiance : … ») sans que
  leur texte ni leur classe `is-*` soient modifiés.
- **Impact** : le sens du type et de la confiance est disponible au survol et
  pour tout outil, sans ajouter de couleur comme unique porteur d'information.
- **Risque** : les valeurs sont relevées dans le jeu de données réel ; une valeur
  inconnue retombe sur le token brut (`label(map, token)`), jamais sur une
  étiquette inventée. Le `title` est complémentaire du texte visible, il ne le
  remplace pas.
- **Effort** : S.
- **Vérification** : `4/4` points typés avec libellés ; `8` attributs `title`
  (deux par point) sur la fiche France.

## E12-05 — Provenance implicite : source et texte du point non reliés

- **Problème / preuve** : `chronology.js:490-496` construit une `<ul class="point-sources">`
  de `<li data-source-id>` sous le point. La relation « ce texte est étayé par
  cette source » repose uniquement sur l'imbrication DOM ; aucun attribut ARIA ne
  la rend explicite. Le jeu de données contient des URL de sources, qui ne doivent
  surtout pas être rendues (atlas zéro réseau).
- **Solution** : `stampSources()` donne à la liste un identifiant unique
  `chronology-sem-src-<repère>-<rang>`, pose `data-sem-role="source-list"` et
  `data-sem-source-id` sur chaque item, et **ajoute** cet identifiant à
  l'`aria-describedby` du paragraphe de texte du point via `addId()` (sans écraser
  une valeur existante). Aucune URL n'est émise.
- **Impact** : la provenance devient une relation adressable et annonçable ; un
  lecteur d'écran peut entendre les sources après le texte du point.
- **Risque** : `aria-describedby` sur une liste lit tous ses items — volontaire,
  mais limité aux quelques sources réellement attachées (3 sur la fiche France).
  L'identifiant est « slugifié » et borné à 64 caractères pour rester valide.
- **Effort** : M.
- **Vérification** : `3/3` sources typées, `2` paragraphes reliés (deux points
  portent des sources, l'un avec deux références), couverture `3/3`.

## E12-06 — Repères : pas de clé stable ni de rang global adressable

- **Problème / preuve** : le `li` porte `data-event-id` (`:379`) et
  `data-importance` (`:382`), mais le rang global n'apparaît que dans le texte de
  `#atlas-chrono-status` (`:247`) et de l'`aside-kicker` — et uniquement pour le
  repère courant. La liste affichée ne contient que les repères de l'ère courante
  (ou un sous-ensemble filtré) : son ordre ne donne donc pas le rang global.
- **Solution** : `eventIndex()` construit une table `id → { ordinal, eraId,
  importance }` depuis `DATASET.countries` (module local, aucune requête). Chaque
  `li` reçoit `data-sem-id`, `data-sem-ordinal` (1-indexé), `data-sem-era-ref`,
  `data-sem-importance` et une clé composée `data-sem-key`
  (`pays/ère/repère`) ; la carte reçoit `data-sem-ref`.
- **Impact** : un repère reste adressable même sous filtre, et sa hiérarchie
  pays → ère → repère est explicite dans le DOM.
- **Risque** : l'importance reste un rang ordinal observé (`1`, `2`, `3`) ; le jeu
  de données ne définit pas d'échelle sémantique plus fine, qui n'est donc pas
  inventée (E12-08 le documente).
- **Effort** : S.
- **Vérification** : `3/3` repères typés avec clé composée ; `data-sem-key`
  conforme à `france/france-era-1/fr-massalia` pour le premier repère.

## E12-07 — Contexte courant absent de la racine de la vue

- **Problème / preuve** : `.chronology-layout` ne porte que `data-country-id`
  (`:215`). L'ère et le repère actifs sont signalés par `aria-current="true"`
  (`:290`, `:390`) sur des boutons profonds : un outil doit parcourir tout le DOM
  pour reconstituer la sélection.
- **Solution** : la racine reçoit `data-sem-scope="chronology"`,
  `data-sem-country-id`, `data-sem-era-id`, `data-sem-event-id` et la
  clé composée `data-sem-key`, dérivés des seuls états ARIA déjà posés par la vue.
  Aucun import du store, aucune écriture d'état : la lentille reste observatrice.
- **Impact** : l'instantané rendu est décrit en un seul endroit, stable pour les
  tests et pour une éventuelle sérialisation.
- **Risque** : si aucun repère n'est sélectionné (ère vide), les champs ère/repère
  sont des chaînes vides — un état explicite, pas une valeur par défaut trompeuse.
- **Effort** : S.
- **Vérification** : `{"c":"france","e":"france-era-1","r":"fr-massalia"}`
  relevés sur la racine au premier rendu.

## E12-08 — Aucun dictionnaire : les termes ne sont jamais définis

- **Problème / preuve** : `<time>` ISO, rangs globaux, `kind`, `confidence`,
  `importance`, source, clé composée : aucun de ces termes n'est défini dans la
  page. Les valeurs sont compréhensibles par le développeur, pas par le lecteur.
- **Solution** : un `<details id="chronology-e12-dictionary">` plié par défaut est
  ajouté en fin de colonne principale, avec neuf définitions en texte réel
  (`<dl>/<dt>/<dd>`), dont les domaines de valeurs **observés** dans le DOM
  (types, confiances) et la règle d'écriture des années négatives. Le résumé est
  un contrôle natif focusable, avec `:focus-visible` et 30 px de hauteur minimale.
- **Impact** : vocabulaire et conventions sont consultables sans quitter la vue,
  sans texte caché ni région live, et sans encombrer le rendu par défaut.
- **Risque** : le contenu du `<details>` est dans le DOM mais replié ; il ne
  prétend pas remplacer une documentation hors ligne. Les définitions sont
  dérivées du DOM courant : sur une ère sans point, les listes de valeurs
  affichent « aucun point affiché » plutôt qu'une liste vide muette.
- **Effort** : M.
- **Vérification** : un seul dictionnaire, `open === false` au chargement,
  neuf paires `<dt>/<dd>`, texte lisible et responsive sous 620 px.

## E12-09 — Aucune surface d'audit de la couverture d'annotation

- **Problème / preuve** : rien ne prouve, une fois les 100 lentilles appliquées,
  que celle-ci a bien annoté tous les nœuds éligibles ; les `data-*` sont invisibles
  au relecteur occasionnel.
- **Solution** : `#chronology-e12-coverage` affiche
  `repères typés / points typés / années datées / sources reliées` et les mêmes
  ratios sont miroirés sur la racine (`data-sem-coverage-events|points|years|sources`).
  Aucune région `aria-live` supplémentaire : le filtrage réécrit la vue à chaque
  frappe et `#nav-c2a-live` reste l'unique annonceur.
- **Impact** : la couverture est lisible, falsifiable et vérifiable par un test
  automatique, sans journalisation.
- **Risque** : les dénominateurs sont ceux du rendu courant (ère filtrée). C'est
  volontaire : l'audit porte sur ce qui est affiché, pas sur tout le pays.
- **Effort** : S.
- **Vérification** : `3/3 · 4/4 · 3/3 · 3/3` sur France, texte stable après
  filtrage et retour à un filtre vide.

## E12-10 — Re-render : risque de doublons et d'annotations perdues

- **Problème / preuve** : la coque reconstruit le contenu de `#atlas-stage` à
  chaque émission du store (voir `src/ui/shell.js:137`) ; `chronology.js:538-539`
  append un nouveau layout puis rejoue les 100 greffons. `registry.js` ne garantit
  que le style (`cssOnce`), pas les nœuds : une lentille naïve accumule les
  panneaux ou réécrit deux fois le même nœud.
- **Solution** : marqueur `data-sem-annotated` sur le layout (retour anticipé si
  l'annotation a déjà eu lieu), gardes `querySelector` avant chaque création de
  nœud, `addId()` pour composer les `aria-describedby`, aucun écouteur, aucun
  minuteur, aucune référence module-level vers le DOM. Le style unique passe par
  `ctx.css('chronology-e12', …)`.
- **Impact** : vingt cycles de rendu produisent exactement un style, un
  dictionnaire et une ligne de couverture, sans ID dupliqué ni erreur console.
- **Risque** : le layout est reconstruit, donc le marqueur disparaît avec lui —
  c'est le comportement voulu. Si la même instance était retraitée, la seconde
  passe est un no-op. Les nœuds ajoutés vivent dans `main`/`aside`, donc hors du
  champ de marquage du tiroir de diagnostic (parents directs uniquement).
- **Effort** : M.
- **Vérification** : 20 allers-retours et deux filtrages successifs en Chromium :
  aucun ID dupliqué, `1/1/1` pour dictionnaire/couverture/style, zéro erreur de
  page ; `node --check src/views/chronology/E012.js` OK.
