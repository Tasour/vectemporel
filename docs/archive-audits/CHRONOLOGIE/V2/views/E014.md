## E014-01 — Ancrage du badge : aucun récapitulatif dédié dans la barre d'outils

- **Problème / preuve** : le modèle de qualité situe les contrôles de périmètre dans `#atlas-chrono-tools` et le champ dans `#atlas-chrono-search` (`E049.md:31-33`, `E049.js:36-37`). Ces références décrivent la recherche, les puces et la réinitialisation, mais aucun emplacement ne porte la synthèse du périmètre : l'utilisateur doit reconstruire mentalement l'état à partir de plusieurs contrôles éparpillés.
- **Solution** : `E014.js:26` déclare `BADGE_ID = 'chronology-v2-e014-badge'` ; `:194` choisit l'hôte `#atlas-chrono-tools`, avec repli sur `#atlas-chrono-main` puis `ctx.layout` ; `:195-197` crée le `<section role="region" aria-labelledby="chronology-v2-e014-title">`. Le CSS `:43-49` en fait un bloc en flux normal (`flex: 1 1 100%`), jamais une modale ni un calque.
- **Impact** : le récapitulatif a une adresse DOM stable, lisible et auditable, sans déplacer ni renommer les contrôles existants.
- **Risque** : si `#atlas-chrono-tools` disparaît d'un rendu, le repli `#atlas-chrono-main` conserve le badge, mais celui-ci se retrouve hors de la barre d'outils ; le comportement reste visible et non cassant. Aucun sélecteur de test existant n'est renommé.
- **Effort** : S.
- **Vérification** : relecture `E014.js:26, 194-197` ; harnais — après rendu, un seul `#chronology-v2-e014-badge` est rattaché à `#atlas-chrono-tools`, avec `role="region"` et `aria-labelledby` valide.

## E014-02 — Phrase de synthèse visible : périmètre jamais résumé en une lecture

- **Problème / preuve** : l'indice de la vue est réduit à une ligne de 8 px (`E049.md:23`) et la recherche décrit purement la mécanique de frappe (`E049.md:31-33`) : aucune phrase ne dit « ce que je regarde en ce moment ». Les états sont donc lisibles individuellement, jamais synthétisés.
- **Solution** : `E014.js:133-141` définit `summarize()` : « Périmètre complet : aucun filtre actif, tous les repères sont affichés. » ou « Périmètre filtré — recherche « … » · types de points : … . ». `:201` crée le paragraphe `#chronology-v2-e014-summary` ; `:169` l'écrit via `write()` (`:105-107`), dédupliqué ; `:170` porte le texte intégral dans `title`.
- **Impact** : l'état du périmètre se lit en une phrase, sans ouvrir la modale d'aide ni interpréter plusieurs contrôles.
- **Risque** : la phrase décrit l'état lu dans le DOM au moment du rendu ; si un filtre change sans reconstruire le DOM, elle ne se met pas à jour toute seule — hypothèse explicitée au chantier E014-10 et dans les limites.
- **Effort** : S.
- **Vérification** : harnais — sans filtre, `#chronology-v2-e014-summary` contient « Périmètre complet » ; avec une recherche « ptolemaïque », il contient « recherche « ptolemaïque » » ; deux appels de `refresh()` laissent le même `textContent`.

## E014-04 — Critères actifs non décomposés en puces sémantiques

- **Problème / preuve** : le modèle décrit des puces de filtre comme boutons (`E049.md:50` sur les bandes/cartes, `E049.md:31-33` sur la barre d'outils) et la thématique voisine E012 exige un état explicite par type de point (`themes.json:12`). - **Solution** : `E014.js:113-131` relève la recherche et les puces `button[aria-pressed="true"]` ; `:143-149` fabrique un `<li class="e014-chip">` par critère avec le genre (« Recherche », « Type », « Périmètre ») et la valeur ; `:172-180` reconstruit la `<ul id="chronology-v2-e014-chips">` seulement quand la signature change, via `replaceChildren` ; `:58-64` fournit le style en puces.
- **Impact** : chaque critère est un élément de liste distinct, énonçable et comptable, sans dépendre d'un code de couleur.
- **Risque** : le libellé est pris dans `aria-label` ou `textContent` de la puce source (`E014.js:123`) ; un libellé très long est dédupliqué par `Set` (`:119-127`) mais n'est pas abrégé, ce qui peut allonger la colonne.
- **Effort** : M.
- **Vérification** : relecture `E014.js:143-149, 172-180` ; harnais — recherche + deux puces actives → trois `<li>`, libellés préfixés, `data-e014-signature` mis à jour une seule fois.

## E014-05 — Aucun compteur de critères (distinct du nombre de résultats E015)

- **Problème / preuve** : `themes.json:16` confie à E014 le « badge de récapitulatif du périmètre actif » et `themes.json:17` confie à E015 le « nombre de résultats en role=status (unique) ». Ce sont deux grandeurs différentes : le nombre de critères et le nombre d'événements. Sans compteur de critères, le récapitulatif ne peut pas dire combien de contraintes sont combinées, et le risque de doublon avec E015 est réel.
- **Solution** : `E014.js:130` calcule `criteria = (query ? 1 : 0) + types.length` ; `:182` écrit « Critères actifs : N (recherche : 0/1 · types : k) » dans `#chronology-v2-e014-count` ; `:184` répète `critères : N` dans la ligne de métrique. Aucun `role="status"`, aucun `aria-live` : la grandeur n'entre pas en compétition avec E015 (`E049.md:59-62` sur les régions live existantes).
- **Impact** : la complexité du filtre est chiffrée et falsifiable, sans occuper le canal d'annonce unique de la vue.
- **Risque** : la somme compte la recherche comme un critère unique, quel que soit le nombre de mots ; c'est un choix de définition documenté dans le libellé, pas le nombre de résultats affichés.
- **Effort** : S.
- **Vérification** : relecture — zéro `role="status"` et zéro `aria-live` dans `E014.js` ; harnais — recherche vide + une puce → « Critères actifs : 1 », recherche « x » + deux puces → « Critères actifs : 3 ».

## E014-06 — Aucune traçabilité non bavarde de l'état du filtre

Écrire l'état du périmètre dans une région existante produirait des annonces redondantes à chaque frappe ; pourtant un état vérifiable en dehors du texte libre fait défaut.

- **Risque** : la requête brute est stockée dans un attribut DOM ; elle est issue du champ de recherche existant et n'est ni échappée ni interprétée — le texte passe toujours par `textContent` (`E014.js:106`, `:183`), jamais par `innerHTML`.
- **Effort** : S.

## Blocages / limites inter-domaines

- Le badge est purement descriptif et observationnel : il ne peut pas modifier le champ `#atlas-chrono-search`, les puces de filtre, le `focusIntent` de la vue, le routeur clavier ni la coque — tous fichiers non possédés (`E049.md:31-41`).
- Le relevé des types actifs repose sur `button[aria-pressed="true"]` dans `#atlas-chrono-tools` (`E014.js:121`). Si une lentille voisine change ce contrat (par exemple un `radiogroup` pour un choix unique, cf. `themes.json:43`), le décompte doit être relu ; la lentille E014 n'impose aucun changement aux contrôles sources.
- Le compteur `criteria` additionne la recherche (0 ou 1) et les types actifs : il mesure la complexité du filtre, pas le nombre d'événements. Le nombre de résultats appartient à E015 (`themes.json:17`) et reste porté par sa propre région `role="status"`, que E014 n'écrase pas.
- Le périmètre est relu à chaque rendu, pas observé en continu : un changement de filtre qui ne reconstruirait pas le DOM laisserait le badge afficher l'état précédent. L'ajout d'un `MutationObserver` sortirait du périmètre de cette lentille et risquerait d'écrire dans la zone observée.
- L'état affiché (compteurs, requête, types) est volatile : il est recalculé à chaque rendu, comme le prescrit le contrat de greffon (`registry.js:28-43`). Les attributs `data-e014-*` sont un miroir de lecture, pas une source de vérité.
